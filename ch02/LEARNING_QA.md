### OpenAI Function Calling 官方文档：协议细节
一句总结：这篇文档最核心的是把工具调用拆成 3 段：工具声明、模型返回 `tool_calls`、工具结果回填。

详细内容：
- 请求里怎么声明工具
  - 在请求体中传 `tools`。
  - 每个工具本质上是一份函数签名：`name`、`description`、`parameters`。
  - `parameters` 使用 JSON Schema，告诉模型参数类型、必填项和约束。
  - 文档提到 `strict: true` 会启用更严格的 schema 约束；在 Chat Completions 中，不开时默认不是 strict。
- 响应里怎么返回工具调用
  - 当模型决定调用工具时，会在 `assistant` 消息里返回 `tool_calls`。
  - 每个 `tool_call` 至少包含：
    - `id`
    - `type`
    - `function.name`
    - `function.arguments`
  - 其中 `function.arguments` 是 JSON 字符串，不是已经解析好的对象。
- 工具结果怎么回填
  - 工具执行结束后，必须追加一条 `role: "tool"` 的消息到 `messages`。
  - 这条消息需要带上：
    - `tool_call_id`
    - `content`
  - `tool_call_id` 的作用是把结果绑定回对应的工具调用。
- `tool_choice` 和 `parallel_tool_calls`
  - `tool_choice: "auto"`：模型自己决定是否调用工具。
  - `tool_choice: "required"`：要求本轮必须调用工具。
  - `tool_choice: "none"`：禁止工具调用。
  - 也可以强制指定某个工具。
  - `parallel_tool_calls: false` 可以禁止一轮同时调多个工具。
- 流式下的工具调用
  - 流式返回时，工具调用信息会出现在 `delta.tool_calls` 中。
  - `function.arguments` 可能被拆成多段，需要客户端按 `index` 自己拼接。
  - 不能假设单个 chunk 就带完整参数。
  - 正确处理步骤：
    1. 按 `tool_call.index` 聚合同一个调用。
    2. 把每个 chunk 里的 `function.arguments` 片段不断追加。
    3. 等这一轮流式响应结束，或能确认参数已经完整。
    4. 再反序列化参数并执行 tool call。
- 这篇文档里最值得记住的坑
  - `strict: true` 会直接影响 schema 约束效果。
  - `function.arguments` 需要你自己反序列化。
  - 工具结果回填必须使用 `role: "tool"` 和 `tool_call_id`。
  - 如果允许并行工具调用，Agent Loop 复杂度会明显上升。
  - 流式模式下，工具参数需要自己聚合。

示例：`list_dir` 工具的 schema
```json
{
  "type": "object",
  "properties": {
    "path": {
      "type": "string",
      "description": "directory path to inspect; use . for the current directory"
    },
    "include_hidden": {
      "type": "boolean",
      "description": "whether to include hidden files such as .env"
    }
  }
}
```

注意：
- 字段是否可选，取决于它是否出现在 `required` 里。
- 不写 `required`，默认所有字段都可选。
- Schema 负责“要不要传”，代码负责“没传时默认值怎么处理”。
- 这个工具里，`path` 为空时默认使用当前目录 `.`。

增强版示例：加入 `enum` 和整数约束
```json
{
  "type": "object",
  "properties": {
    "path": {
      "type": "string",
      "description": "directory path to inspect; use . for the current directory"
    },
    "include_hidden": {
      "type": "boolean",
      "description": "whether to include hidden files such as .env"
    },
    "sort_by": {
      "type": "string",
      "enum": ["name", "size", "modified_time"],
      "description": "how to sort the entries; defaults to name"
    },
    "sort_order": {
      "type": "string",
      "enum": ["asc", "desc"],
      "description": "whether to sort ascending or descending; defaults to asc except modified_time which defaults to desc"
    },
    "max_entries": {
      "type": "integer",
      "description": "maximum number of entries to return; defaults to 200"
    }
  }
}
```

这个增强版主要体现两点：
- `enum` 能限制模型只在固定值里选择，减少乱传参数。
- `integer` 适合表达“数量/上限”这类参数，比字符串更稳定。
- 当排序方向本身也有语义时，最好拆成单独的 `sort_order` 参数，而不是隐含在 `sort_by` 里。

### JSON Schema 设计：如何写得更“模型友好”
一句总结：Schema 不只是给程序校验，更是在给模型写“调用说明书”。

详细内容：
- `required`
  - 作用：告诉模型哪些参数必须提供。
  - 经验：只有“不传就无法执行”的参数才放进 `required`。
  - 能在代码里补默认值的参数，尽量保持可选。
- 类型约束
  - 作用：减少模型乱传值。
  - 经验：能用 `boolean` 就不用 `"yes"/"no"` 字符串；能用 `integer` 就不用字符串数字。
  - 参数结构复杂时，用 `object` 或 `array`，不要把所有信息塞进一个大字符串。
- 枚举 `enum`
  - 作用：把值限制在一个有限集合里，显著提高调用稳定性。
  - 经验：只要值域固定，就优先考虑 `enum`。
- 字段描述 `description`
  - 作用：告诉模型这个字段做什么、什么时候传、格式是什么。
  - 经验：描述里尽量写清用途、格式、默认行为，而不是只写一个名词。

怎么写得更模型友好：
- 参数名要直接，如 `include_hidden`，不要起模糊名字。
- 描述要具体，最好带用途和默认行为。
- 类型尽量收窄，别把所有参数都定义成 `string`。
- 必填字段要克制，避免模型每次都要补很多无关参数。
- Schema 里的可选/必填设计，要和代码里的默认值逻辑一致。

## Q&A

## Q1. `tools`、`tool_calls`、`tool` 消息在协议里分别是什么角色？
一句总结：`tools` 是能力声明，`tool_calls` 是模型决策，`tool` 消息是执行反馈，三者构成闭环。

详细回答：
- `tools`：在请求中告诉模型“有哪些工具可用、每个工具的参数 schema 是什么”。
- `tool_calls`：模型在某一轮决定要调用哪些工具，并给出参数。
- `tool` 消息：工具执行后的真实结果回填给模型，作为下一轮推理输入。
- 闭环流程：用户问题 -> 模型产出 `tool_calls` -> 执行工具 -> 回填 `tool` 消息 -> 模型继续推理或结束。

## Q2. Agent Loop 的状态机应该怎么理解？
一句总结：最小状态机是 `Plan -> Act -> Observe -> Decide`，核心是明确继续/停止条件。

详细回答：
- `Plan`：模型判断是否需要工具、需要哪个工具。
- `Act`：按 `tool_calls` 执行对应工具。
- `Observe`：把工具结果写回消息链。
- `Decide`：若无新的 `tool_calls` 则结束，否则继续下一轮。
- 防失控关键：最大步数、请求总超时、错误中断策略。

## Q3. 为什么工具结果必须回填到 `messages`？
一句总结：模型看不到外部世界，回填结果是它继续推理的唯一证据链。

详细回答：
- Chat Completions 是无状态推理，不会自动记住工具做过什么。
- 不回填会导致模型不知道执行结果，容易幻觉、重复调用或错误决策。
- 回填后模型才能基于“真实观察”做下一步动作或收尾回答。

## Q4. 一个“模型友好”的工具接口应该满足什么标准？
一句总结：可描述、可验证、可观测，是工具设计的三条主线。

详细回答：
- 可描述：工具名和描述清晰，模型能判断“何时该用它”。
- 可验证：参数 schema 明确类型/必填/约束，降低错误调用。
- 可观测：输出结构化，成功与失败都可被模型解释和利用。
- 副作用可控：高风险操作要有边界说明与策略限制。

## Q5. 工具失败后，Agent 应如何处理“错误语义”？
一句总结：失败不是终点，而是下一轮推理输入；关键在于区分可恢复与不可恢复错误。

详细回答：
- 可恢复错误：路径不存在、参数错误、权限不足等，可修正后重试。
- 不可恢复错误：安全策略禁止、系统级失败等，应尽快终止并上报。
- 实践原则：把错误细节回填给模型，避免盲目重复调用。

## Q6. 为什么要做终止条件和成本控制？
一句总结：没有边界的 tool loop 会失控，带来高成本、高延迟和高风险。

详细回答：
- 必备终止条件：无 `tool_calls`、达到最大步数、超时、策略中断。
- 成本控制手段：限制轮数、裁剪上下文、限制工具输出长度。
- 风险后果：循环调用、token 暴涨、响应变慢、系统不稳定。

## Q7. `ch02` 里最关键的安全问题是什么？
一句总结：高风险工具（尤其 `bash`）需要最小权限边界，否则 Agent 可能执行危险操作。

详细回答：
- 最小防护集合：命令白名单、路径限制、执行确认、沙盒隔离、审计日志。
- 原因：模型可能受幻觉或注入影响，单靠 prompt 无法保证安全。
- 结论：安全必须落在“工具执行层”的硬约束，而不是只靠模型自觉。

## Q8. Prompt 在 Tool Loop 中的职责是什么？
一句总结：Prompt 负责行为策略约束，工具层负责权限边界控制，二者缺一不可。

详细回答：
- Prompt 规定模型行为：先读后改、失败先分析、不要预言工具结果。
- Prompt 影响决策风格：何时调用工具、何时直接回答。
- 但 Prompt 不是安全机制：真正的安全要靠工具白名单/沙盒/权限控制。

## Q9. “防失控”具体在防什么？为什么 Agent 会失控？
一句总结：防失控是在防无界循环、资源暴涨和危险动作；失控来自概率决策与缺乏硬边界的叠加。

详细回答：
- 防的三类问题：
  - 逻辑失控：模型反复调用工具却不收敛到最终答案。
  - 资源失控：轮次增长导致上下文膨胀，token、延迟和成本持续上升。
  - 安全失控：高风险工具被误用，触发不安全操作。
- 失控原因：
  - 模型是概率决策，不保证一步到位；
  - 工具执行可能失败，模型可能错误重试；
  - 上下文越长越嘈杂，决策稳定性下降；
  - 没有步数/超时/权限等硬边界时，循环缺少停止约束。
- 典型防护：
  - `maxSteps`、请求总超时、输出截断、工具权限限制（白名单/沙盒）。

## Q10. Tool Calling 机制本身有哪些不足？
一句总结：Tool Calling 提升了执行能力，但同时引入了不确定性、复杂性和更大的安全面。

详细回答：
- 不确定性高
  - 模型可能选错工具、传错参数、重复调用，行为稳定性弱于纯规则系统。
- 延迟与成本上升
  - 每次工具调用都增加一轮交互，复杂任务会明显变慢、token 费用升高。
- 错误链放大
  - 任一工具输出异常都会污染后续推理，形成连锁偏差。
- 安全面扩大
  - 接入 `bash`、写文件、网络等能力后，风险从“回答错误”升级为“执行错误”。
- 可观测性与调试复杂
  - 问题可能出在 prompt、schema、执行层、回填格式，定位难度高。
- 协议耦合与漂移
  - 模型版本、SDK 版本、工具 schema 调整都可能导致行为变化，维护成本增加。

## Q11. 为什么“列出最近修改的几个文件”这个请求里，模型先调用 `list_dir`，又补了一次 `bash`？
一句总结：这是一个典型的“模型友好性不足 + 工具集竞争”案例，说明专用工具还没有完整覆盖用户意图。

详细回答：
- **现象：**  
  用户意图明明是“列出最近修改的几个文件”，预期调用应当是 `list_dir {"path": ".", "sort_by": "modified_time", "sort_order": "desc", "max_entries": 5}`，但模型实际先调用了 `list_dir {"path": ".", "sort_by": "modified_time"}`，随后又补了一次 `bash {"command": "ls -lt | head -20"}`。
- **说明：**  
  这说明模型没有完全相信 `list_dir` 一次就能满足这个任务，而是把 `bash` 当成了更强的兜底工具，去补足“最近修改”这个需求。
- **可能原因：**  
  这通常不是单一的 schema 问题，而是几件事叠加：
  - `list_dir` 的输出里没有修改时间，只返回文件名，模型难以确认结果是否真的体现“最近修改”。
  - `sort_by = modified_time` 只表达了排序字段，没有表达排序方向，而用户真正想要的是“最新在前”。
  - `max_entries` 虽然存在，但不是必填，模型未必稳定把“几个文件”映射成具体数量。
  - `bash` 过于通用，只要专用工具表达稍弱，模型就容易转向它。
- **从模型友好性角度看：**  
  这个 case 的本质是 schema 约束还不够精确，tool description 还不够强，tool output 还不够贴近用户意图，同时工具集里还存在一个更强的通用工具 `bash`。

## Q12. [重点] 遇到更复杂的 Tool Calling case 时，应该怎么判断和调试？
一句总结：复杂 case 的 debug，不是看模型聪不聪明，而是看：意图、schema、执行结果、回填链路，哪一层让模型失去了确定性。

详细回答：
- **工具选择问题：**  
  先判断是“选错工具”还是“用错工具”。选错工具，是本该调 `list_dir` 却去调了 `bash`；用错工具，是工具选对了，但参数错了，或者结果没法满足用户意图。这是排查的第一刀，因为这两类问题后续方向完全不同。
- **问题分层：**  
  再看问题落在哪一层：
  - 用户意图表达层，query 本身含糊，比如“最近几个文件”到底是 5 个还是 10 个。
  - Prompt/策略层，系统提示没有明确“优先用专用工具，不要轻易 fallback 到 bash”。
  - Tool schema 层，参数设计不贴近任务语义，描述不清，枚举、必填和默认值不合理。
  - Tool 执行与输出层，执行结果不够可信、缺关键字段，或者返回格式不利于下一轮推理。
- **观察点：**  
  真正 debug 时，固定看 5 个观察点最有效：
  - 用户 query 有没有歧义。
  - 发给模型的 `tools` 定义是否足够清楚，尤其是 `description`、`parameters`、`enum`、`required`。
  - 模型实际返回了什么 `tool_calls`，参数具体怎么传。
  - 工具执行结果是否真正把用户关心的信息返回了。
  - 回填后模型下一轮是在修正、继续，还是偏离并 fallback 到通用工具。
- **判断框架：**  
  这里有一个很好用的判断框架：这个工具“能不能做”这个任务，模型“知不知道它能做”这个任务，模型“能不能确认它已经做对了”。你前面的 `list_dir` case，本质上就是第 3 个问题最明显：工具其实能做，但模型看不到修改时间，所以无法确认自己做对了。
- **常见归因：**  
  - 模型不调用专用工具，反而调用 `bash`，通常是专用工具描述弱、输出弱，或者 prompt 没强调优先级。
  - 模型调了对的工具但参数不全，通常是 schema 约束不足，或者 query 本身不够明确。
  - 模型调完工具还继续乱调，通常是工具输出没有直接回答用户问题，导致模型不敢收尾。
  - 模型反复重试同一个工具，通常是错误信息不够具体，模型不知道该怎么修正。
- **调试建议：**  
  后面遇到复杂 case，建议固定保留原始 query、本轮 `messages`、`tools` schema、每轮 `tool_calls`、每轮 tool result 和最终 answer。这样你就能做“回放式调试”，而不是靠印象猜。

## Q13. [重点] 当 `max_entries` 这类“数量限制”参数既想保持可选，又不想默认返回全量时，应该怎么设计？
一句总结：这不是模型的锅，也不该简单归因到 schema；本质上是产品语义默认值设计问题。

详细回答：
- **冲突点：**  
  这里有两个目标天然冲突：不传 `max_entries` 时，希望工具足够通用，能返回全量；但用户说“几个文件”时，又希望模型自动收敛成小结果集，避免过重。这不是单靠模型能稳定解决的，因为“几个”本来就是模糊语义。
- **更稳的默认设计：**  
  更稳的设计通常是把 `max_entries` 保持可选，但不传时不要真返回全量，而是返回一个安全默认值，比如 `50`，同时在返回里显式说明是否被截断，例如 `truncated=true, returned=50, total=312`。这样模型不传时不会炸，用户明确要更多时，模型也可以再调一次，显式请求更大的 `max_entries`。
- **description 的作用：**  
  还有一个很重要的点，是在 description 里把默认行为写得非常明确。这比改系统 prompt 更直接有效，因为这是 tool-local 语义。比如你可以把 `max_entries` 描述成：“If omitted, the tool returns up to 50 entries by default. Use a small number for requests like 'a few files'.” 系统 prompt 更适合补全局原则，例如“Prefer bounded tool calls over unbounded output”或者“When the user asks for a few/recent/top items, pass an explicit limit”。
- **模糊语义映射：**  
  如果你想让行为更稳定，还可以给模糊语义做产品约定，例如：
  - “几个”默认映射成 `5`。
  - “一些”默认映射成 `10`。
  - “前几个”默认映射成 `5`。
  这不是模型真的懂了中文，而是你在系统策略里给了一个 operational rule。
- **更进一步的设计：**  
  如果工具本身比较重，最稳的设计往往不是一个接口兼顾所有场景，而是把它拆成“预览”和“全量”，或者直接做成分页风格，例如 `page_size`、`page_num`。这样默认先返回一页，模型如果想拿全量，会更自然地学会循环调用。
- **结论：**  
  这不算模型“犯错”，而是工具设计者要定义默认行为边界。最好不要把“不传 `max_entries` = 真全量返回”当作默认，更合理的方式是不传时走安全上限，需要更多时再显式请求。

## Q14. [重点] 设计 tool 时，需要注意哪些问题，才能尽量避免常见踩坑？
一句总结：tool 设计不是“功能实现”问题，而是“让模型稳定、低成本、可验证地使用这个能力”的问题。

详细回答：
- **能力边界：**  
  工具到底能做什么、不能做什么，要表达明确，不要让模型以为工具能完成一个其实只能部分完成的任务。比如既然支持按修改时间排序，输出里最好真的带修改时间。
- **参数语义：**  
  不要只给一半语义。像 `sort_by` 只表达“按什么排”，没表达“怎么排”，就容易出歧义；需要独立的语义维度，就拆成独立参数，比如 `sort_by` + `sort_order`。
- **默认行为：**  
  可选参数不等于“不传就全量”，默认值应该偏安全、偏保守、偏低成本，真要更大范围，再让模型显式请求下一步。
- **输出设计：**  
  模型不仅要“调用成功”，还要“看得出来成功”。返回值里要包含用户关心的关键证据字段，否则模型会继续补调别的工具去验证。
- **Schema 贴近用户语言：**  
  参数设计不要只站在实现者视角，要考虑用户会怎么表达需求，模型会怎么映射语义。枚举、整数、布尔这些强约束要尽量用，少让模型自由发挥字符串。
- **工具竞争：**  
  只要有 `bash` 这种万能工具，专用工具描述稍弱就容易被抢走，所以专用工具必须在 description、schema、输出上都更“像正确答案”。
- **调试友好：**  
  提前想好出问题时你要看什么。一个好 tool 应该容易观察模型为什么选它，参数为什么这么传，以及输出为什么不足以让模型收尾。
