# 第六章学习笔记

## 学习导航

### 1. 本章需要学习的内容

- **记忆系统为什么独立于上下文工程：**
  第五章解决的是“当前会话在有限窗口里怎么运行”，第六章开始解决“跨会话之后，什么信息应该被长期保留”。你要区分上下文治理和长期记忆的职责边界，否则后面很容易把 `memory`、`offload`、`summary` 混成一件事。

- **两层记忆架构为什么成立：**
  本章不是做一个统一的大记忆文件，而是拆成 `Global Memory` 和 `Workspace Memory`。你要理解这个分层不是存储形式差异，而是作用域和生命周期差异：一个描述用户长期偏好，一个描述当前工作区知识。

- **Memory 接口和 MemoryUpdater 接口为什么分开：**
  `Memory` 负责对外暴露记忆和持久化更新，`MemoryUpdater` 负责“怎么从新消息里提取并生成新记忆”。这和 `ch05` 里 `SummaryPolicy` / `Summarizer` 的分层很像，核心都是把“策略容器”和“生成实现”拆开。

- **记忆更新为什么要走 LLM：**
  本章没有写死规则去提取偏好和项目信息，而是让 LLM 根据旧记忆和新消息生成更新后的记忆。你要重点理解这里的收益和代价：收益是抽取能力强，代价是成本、准确率和可控性问题都会被引入。

- **记忆为什么要注入到 system prompt：**
  记忆最终不是为了存下来，而是为了让模型在新一轮请求里真正能用到。所以本章还要看 `memory.String()` 是怎么变成 prompt 片段，再被 `context.Engine.BuildSystemPrompt()` 注入请求的。

- **记忆事件系统为什么出现：**
  和 `policy` 事件类似，记忆更新也会在 TUI 里显示开始、结束、失败状态。这里值得学的不是 UI，而是为什么当系统开始有后台更新动作时，事件可观察性会变成必要能力。

### 2. 本章操作内容

- **准备配置文件：**
  先准备 `config.json`，至少包含前台模型和后台记忆更新模型。前台模型负责主对话，后台模型负责提取和更新记忆。

- **运行本章：**
  直接执行：

```bash
go run ./main
```

- **观察记忆更新事件：**
  在 TUI 里输入类似：

```text
你好，我习惯使用 vim 编辑器
```

  观察界面是否出现 `记忆更新: (已完成)` 之类的状态。

- **检查持久化结果：**
  运行后检查：

```bash
cat ~/.babyagent/memory/MEMORY.md
cat $(pwd)/.babyagent/memory/MEMORY.md
```

  分别确认 `Global Memory` 和 `Workspace Memory` 是否被写入。

- **验证跨会话记忆：**
  先在一次会话里告诉 Agent 项目技术栈或用户偏好，退出重开，再问它关于你的项目或偏好的问题，观察它是否能从持久化记忆中读回这些信息。

### 3. 本章学完需要掌握的知识点

- **上下文工程和记忆系统的边界：**
  你应该能明确解释：`ch05` 的 `offload + summarize + truncate` 解决的是当前会话里的上下文预算，而 `ch06` 的 memory 解决的是跨会话知识保留。

- **两层记忆为什么不是冗余设计：**
  你应该能解释为什么用户偏好不该和项目知识混在同一层里，也能说清楚 `Global` 和 `Workspace` 各自适合保存什么。

- **LLM 更新记忆的完整链路：**
  你应该能顺着代码讲清楚：本轮新消息 -> `MemoryUpdater.Update` -> XML 解析 -> 存储写入 -> `memory.String()` -> system prompt 注入。

- **记忆系统当前的能力边界：**
  你应该知道它已经实现了跨会话持久化，但还没有实现真正的检索式 memory、冲突解决、时间衰减、结构化知识管理。

- **记忆系统引入的新风险：**
  你应该知道记忆不只是“更聪明”，也意味着会引入摘要错误、错误记忆固化、敏感信息持久化、额外 API 成本等问题。

### 4. 扩展阅读与参考资料总结

- **DeepAgent Long-term memory Documentation：**
  这份材料的价值不在于某个 API，而在于它提供了一个更接近工业系统的长期记忆视角。你可以拿它和本章对照，理解本章实现的是“最小可用的跨会话持久化记忆”，而不是完整的 memory architecture。

  原始链接：
  - https://docs.langchain.com/oss/python/deepagents/long-term-memory

  原文里有几个点值得和 `ch06` 对照学习。

  - **DeepAgents 把长期记忆做成 filesystem-backed memory。**
    它的核心设计是让 agent 像读写文件一样读写 memory，由 backend 控制这些文件存在哪里、谁能访问。这个思路和 `ch06` 用 `~/.babyagent/memory/MEMORY.md`、`{workspace}/.babyagent/memory/MEMORY.md` 做持久化很接近。但 DeepAgents 更进一步，把 backend、namespace、权限和多租户隔离都放进了设计里。

  - **它明确区分 short-term memory 和 long-term memory。**
    文档把单次会话里的 conversation history、scratch files 归到 short-term memory，把跨会话保存的文件归到 long-term memory。这个边界正好对应我们在 `ch05` / `ch06` 里一直强调的区别：上下文工程管理当前会话状态，长期记忆管理跨会话状态。

  - **它支持两种读取方式：启动时注入和按需读取。**
    memory 可以在 agent 启动时加载进 system prompt，也可以在对话过程中按需读取。文档里用 skills 举例：启动时只读 skill 描述，真正需要时才读完整 skill 文件。这个点很重要，因为它说明“全量注入 system prompt”只是最简单方式，不是唯一方式。`ch06` 当前全量注入 Global / Workspace，是教学版闭环；工业系统更可能做按需召回。

  - **它把 memory 的作用域做成 namespace。**
    文档里有 agent-scoped memory 和 user-scoped memory。agent-scoped memory 让同一个 agent 在所有用户之间共享长期身份和经验；user-scoped memory 则按用户隔离，避免 A 用户偏好泄露给 B 用户。这个和 `ch06` 的 `Global / Workspace` 不是同一个维度：`ch06` 是按信息作用域分层，DeepAgents 同时强调按访问主体隔离。

  - **它把 memory 拆成更细的类型维度。**
    文档提到 memory 可以按持续时间、信息类型、作用域、更新策略、读取方式、写权限来分类。其中信息类型包括 episodic、procedural、semantic。这个比 `ch06` 的两段 Markdown 更完整：`ch06` 目前主要在做 semantic memory，也就是事实、偏好、项目知识；procedural memory 更接近 skills；episodic memory 则保留过去会话和任务过程。

  - **它提出 background consolidation。**
    文档说 memory 可以在对话中热路径写入，也可以在会话之间由后台 consolidation agent 读取近期对话、抽取关键事实、合并进 memory store。这个正好对应我们之前讨论的“每轮都更新是不是开销大”。`ch06` 当前每轮 `CommitTurn()` 后同步更新，是最清楚的教学闭环；DeepAgents 提供了更工业化的方向：把记忆整理移到后台，用 cron 按实际使用频率触发。

  - **它强调 read-only vs writable memory。**
    对用户偏好这类个人记忆，agent 可以有写权限；对组织政策、合规规则、developer-defined skills 这类共享状态，通常应该只读。这个点和我们讨论的 memory 污染、prompt injection 风险直接相关：不是所有能被 agent 读到的 memory 都应该允许 agent 修改。

  - **它专门讨论 concurrent writes。**
    多个线程并发写同一个 memory 文件时，会有 last-write-wins 冲突。文档建议用后台 consolidation 串行化写入，或者按主题拆成多个文件减少竞争。`ch06` 当前没有并发写治理，如果未来支持多会话同时运行，这会成为真实问题。

### 5. 扩展阅读需要重点学习什么

- **重点一：长期记忆和当前上下文的边界。**
  你要特别关注外部材料里是如何区分“本轮上下文”和“长期记忆”的，因为这是本章最容易混淆、但也是最关键的概念边界。

- **重点二：记忆的写入策略。**
  不是所有消息都值得记忆。你后面看扩展阅读时，要重点看“什么信息应该进入长期记忆、什么不应该”。

- **重点三：记忆的读取与注入方式。**
  本章当前是把全部记忆直接注入 system prompt。扩展阅读里如果出现检索式注入、按需召回、结构化记忆注入，这些都值得和本章当前实现做对比。

- **重点四：记忆系统的可靠性问题。**
  包括记忆错误、记忆冲突、过时记忆、敏感信息持久化，这些都是后面继续升级 memory system 时必须面对的问题。

- **重点五：作用域和权限比“记住内容”更重要。**
  DeepAgents 文档里反复出现 namespace、user-scoped、agent-scoped、organization-level、read-only、writable 这些概念。你要把它们理解成 memory governance 的核心：长期记忆不是简单存文本，而是要回答谁能读、谁能写、写入后影响谁。

- **重点六：后台整理不是优化细节，而是 memory system 的另一种架构。**
  Background consolidation 说明记忆更新可以不阻塞主对话，也可以跨多轮对话综合判断。它牺牲的是即时生效，换来更低前台延迟、更好的合并质量和更可控的写入节奏。

### 6. 本章应掌握的核心知识点

- **第六章的主线不是“多存一个文件”，而是把 Agent 从单会话系统推进成跨会话系统。**
  你要把这一章看成“长期记忆子系统”的起点，而不是第五章的附属补丁。

- **两层记忆架构是按作用域分层，不是按格式分层。**
  `Global Memory` 面向跨会话、跨项目的用户长期模式，`Workspace Memory` 面向当前项目的局部知识积累。

- **Memory 和 MemoryUpdater 的分层是这一章的关键接口设计。**
  一个负责持有和更新记忆，一个负责生成新记忆内容。这种分层让后面替换不同更新策略成为可能。

- **记忆最终的作用点是 system prompt。**
  持久化本身不是终点，能在下一轮推理里重新被模型看到，才算形成了真正的记忆闭环。

- **这一章仍然是教学版 memory system，而不是工业级长期记忆系统。**
  它已经实现了跨会话记忆、双层分域、文件持久化和事件可观察性，但还没有做检索、冲突解决、时间衰减、结构化记忆、可信度管理这些更重的能力。

### 7. 建议代码阅读顺序

- **先看 [main.go](./main/main.go)：**
  先看这一章把哪些模块组装起来了。你要重点观察前台模型、后台模型、`contextEngine`、`memoryStorage`、`MultiLevelMemory`、`MemoryUpdater`、`policies`、TUI 分别在什么位置接入。尤其要区分 `tool.NewLoadStorageTool(memoryStorage)` 和真正的长期记忆不是同一个系统。

- **再看 [memory.go](./memory/memory.go)：**
  这是本章最关键的抽象文件之一。你要重点观察 `Memory` 为什么只有 `String`、`Snapshot`、`Update` 三个能力，`MultiLevelMemory` 为什么同时持有 `content`、双存储、`updater`，以及 `MemoryContent.String()` 为什么实际上是 prompt 注入入口。

- **然后看 [update.go](./memory/update.go)：**
  这里决定“记忆怎么被生成”。你要重点观察为什么输入是“旧记忆 + 新消息”，为什么用 XML 标签回传两层记忆，以及 `extractXMLTag()` 这种解析方式的优点和风险。

- **再看 [engine.go](./context/engine.go)：**
  这是 `ch05` 和 `ch06` 的连接点。你要重点观察 `CommitTurn()` 里为什么顺序是“先提交消息，再跑 policy，再更新记忆”，以及 `BuildSystemPrompt()` 是怎么把 `{memory}` 注入系统提示词的。

- **再看 [agent.go](./agent.go)：**
  这里重点看两件事：一是 memory event 是怎么通过 `viewCh` 送到 TUI 的；二是 `MemorySnapshot()` / `MemoryStatus()` 这类方法为什么只服务于可观察性，不参与模型推理。

- **最后看 TUI 相关文件：**
  [vo.go](./vo.go)、[entry.go](./tui/entry.go)、[tui.go](./tui/tui.go)。你要重点观察为什么记忆更新被单独做成 `MessageTypeMemory`，以及 `/memory`、`/memory-status` 这类命令怎样把原本隐式的记忆子系统变成可检查状态。

- **学习时优先盯这 5 个观察点：**
  你要持续问自己：`memory` 和 `offload + load_storage` 的边界是什么；为什么两层记忆按作用域分；为什么记忆更新用后台模型；为什么记忆是通过 system prompt 注入而不是普通消息回流；为什么 memory update 放在 turn 结束后而不是边对话边写。

## Q&A

### Q1. [重点] 为什么 `ch06` 要单独引入一个 `memory` 子系统，而不是继续把长期信息当成 `ch05` 的上下文治理问题？

- **一句总结：**
  `ch05` 解决的是当前会话里的上下文预算，`ch06` 解决的是跨会话之后哪些信息应该长期保留；两者处理的是不同生命周期的问题，所以必须独立成一个记忆子系统。

- **详细回答：**
  `ch05` 的 `truncate / offload / summarize` 都是在治理“当前这次会话发给模型的上下文应该长什么样”。它关心的是当前窗口里保留什么、压缩什么、外置什么，本质上是运行时上下文预算问题。

  但 `ch06` 里要解决的是另一个层级的问题：一次会话结束后，哪些信息值得在下次会话里继续保留。这里面最典型的就是用户长期偏好和项目知识。这些信息不应该跟着一次 turn 的上下文裁剪一起进出窗口，而应该进入一个跨会话、可持久化的系统。

  可以从几个角度理解。

  - **`ch05` 处理的是“当前窗口怎么安排”，`ch06` 处理的是“跨会话之后什么该留下”。**
    前者关心的是在线上下文预算，后者关心的是长期知识沉淀。两者虽然都在处理“历史信息”，但处理的是不同生命周期的问题。

  - **把长期信息继续塞进 `context.Engine`，职责会混掉。**
    `context.Engine` 关注的是一轮请求前后怎样构造和治理消息链；`memory` 关注的是哪些知识应该被沉淀、怎样更新、怎样持久化、怎样在下次请求里重新注入。职责边界已经完全不同。

  - **如果不拆开，系统很容易把“上下文外置”误当成“长期记忆”。**
    更准确地说，`ch05` 里的上下文治理是在决定“当前窗口里在线保留什么”，而 `ch06` 里的记忆系统是在决定“什么值得跨会话长期存在”。如果不把它们拆开，系统很容易把“上下文外置”误当成“长期记忆”，或者把“长期记忆”误当成“简单摘要”。

  所以 `ch06` 单独引入 `memory` 子系统，不是为了代码分包，而是因为 Agent 到这一章开始真正进入“长期状态管理”问题，这已经超出了上下文工程本身。

### Q2. [重点] 为什么本章要用两层记忆（Global / Workspace），而不是一个统一的大记忆文件？

- **一句总结：**
  两层记忆是按作用域分层：`Global` 保存跨项目、跨会话的用户长期模式，`Workspace` 保存当前项目知识；不用统一大文件，是为了避免跨项目污染，并给后续不同治理策略留边界。

- **详细回答：**
  因为这两类信息的作用域、生命周期、更新频率、冲突方式都不一样。放进一个统一大文件，短期省事，后面很快会互相污染。

  可以分几层看。

  - **`Global Memory` 记录的是“用户长期模式”。**
    这类信息通常跨项目、跨会话成立，比如用户习惯用什么编辑器、偏好什么测试方式、喜欢什么输出风格、有哪些长期工作习惯。这些信息不应该因为你切到另一个项目就消失。

  - **`Workspace Memory` 记录的是“当前项目知识”。**
    这类信息只在当前工作区成立，比如项目结构、技术栈、构建命令、部署流程、当前仓库约定。这些信息换个仓库通常就不成立了。

  - **两者不是内容一样，只是分开存。**
    `Global` 解决的是“这个用户长期是什么样”，比如习惯用 `vim`、喜欢 verbose 输出、常用某类工具；`Workspace` 解决的是“这个项目当前是什么样”，比如这个仓库用 `Gin`、测试命令是 `go test ./...`、部署脚本在哪。前者是用户级长期记忆，后者是项目级局部记忆。

  - **如果混成一个大记忆文件，最直接的问题是作用域污染。**
    比如你在项目 A 里学到“这个项目用 React”，切到项目 B 后，这条知识如果还躺在统一记忆里，就可能误导模型。也就是说，项目知识会错误外溢到别的工作区。

  - **用户偏好和项目知识的稳定性也不同。**
    用户偏好通常更新慢、跨会话有效；项目知识更新更频繁，而且经常只在当前仓库有效。拆层后，系统可以自然地允许 `Global` 更稳定、少改，而 `Workspace` 更局部、常改。

  - **这其实也是在按“谁来消费这条记忆”分层。**
    `Global` 更像模型关于这个用户的长期背景知识，`Workspace` 更像模型关于当前项目环境的局部工作记忆。两者虽然最后都注入 system prompt，但它们在语义上不是同一层东西。

### Q3. Global / Workspace 之外，未来还会不会需要第三层，比如 Session Memory？

- **一句总结：**
  未来很可能需要 `Session Memory` 这类第三层，但它不应该替代 `Global / Workspace`，而是专门承接“只在当前会话或当前任务阶段有价值、但又不值得长期沉淀”的中间状态。

- **详细回答：**
  会需要，而且这其实是记忆系统继续演进时很自然的一层。现在 `ch06` 只有 `Global` 和 `Workspace`，是为了先把“用户长期偏好”和“项目长期知识”分开。但真实 Agent 运行时还会出现第三类信息：它们对当前任务很重要，但不一定适合跨会话长期保存。

  可以这样理解三层之间的边界。

  - **`Global Memory` 是用户级长期记忆。**
    它保存跨项目也成立的用户偏好、习惯、稳定背景，比如用户喜欢怎样的回答风格、常用什么工具、对学习笔记有什么格式要求。这类信息通常不应该随着当前任务结束就消失。

  - **`Workspace Memory` 是项目级长期记忆。**
    它保存当前仓库或当前工作区相关的稳定知识，比如项目结构、运行命令、技术栈、约定、当前章节学习方式。这类信息换一个项目后通常不成立，所以不应该进入全局记忆。

  - **`Session Memory` 更像会话级工作状态。**
    它可以保存当前会话里正在推进的目标、阶段性结论、临时约束、用户刚刚给出的任务偏好、已经尝试过但失败的路径。这些信息对当前会话很有用，但未必值得写进长期记忆。

  这层存在的意义，是避免两个极端：如果所有临时信息都写进 `Global / Workspace`，长期记忆会越来越脏，里面会混入大量过期任务状态；如果所有临时信息都只留在上下文窗口里，一旦窗口压缩、摘要错误或会话中断，Agent 又会丢失当前任务的关键状态。

  `Session Memory` 可以被理解为介于“上下文消息列表”和“长期记忆文件”之间的一层。它比普通上下文更结构化，也更容易被系统主动维护；但它的生命周期又比 `Global / Workspace` 短，通常只服务一次会话、一个任务、一个计划，或者一个可恢复的工作流。

  工业系统里，这一层通常会和任务状态、计划状态、未完成 action、临时事实、当前目标绑定在一起。它不一定叫 `Session Memory`，也可能叫 working memory、scratchpad、task state、run state，但本质上都是在解决同一个问题：当前任务需要稳定状态，但这些状态还没有长期价值。

  所以如果后面继续扩展 `ch06`，一个合理方向不是把 `Global / Workspace` 做得越来越大，而是把记忆拆成更清晰的生命周期层级：长期用户记忆、长期项目记忆、会话级任务记忆。这样每一层都有自己的写入标准、过期策略和注入方式。

### Q4. [重点] 为什么 `Memory` 接口和 `MemoryUpdater` 接口要分开，而不是把“怎么更新记忆”直接写死在 `MultiLevelMemory` 里？

- **一句总结：**
  `Memory` 和 `MemoryUpdater` 分开，是因为“记忆怎么持有和存储”与“记忆怎么从新消息里更新出来”是两类不同职责；拆开后才能获得替换性、可测试性和后续演进空间。

- **详细回答：**
  因为 `MultiLevelMemory` 和 `MemoryUpdater` 解决的是两层不同的问题：`MultiLevelMemory` 负责记忆作为状态怎么持有、怎么读、怎么存；`MemoryUpdater` 负责新消息来了以后，记忆内容应该怎么被改写。如果把“怎么更新记忆”直接写死在 `MultiLevelMemory` 里，记忆系统会很快变成一个职责混杂的大对象。

  可以从几个角度看。

  - **`MultiLevelMemory` 更像状态容器。**
    它关心的是当前记忆内容是什么、global / workspace 分别存到哪里、更新后怎么持久化、对外怎么提供 `String()` / `Snapshot()` 这类能力。这些属于“记忆的持有与生命周期管理”。

  - **`MemoryUpdater` 更像更新策略。**
    它关心的是给它旧记忆和新消息后，应该产出什么新记忆；是走 LLM 抽取，还是规则抽取；prompt 怎么写；输出怎么解析；哪些信息应该保留、哪些应该丢弃。这些属于“记忆的生成逻辑”。

  - **这和 `ch05` 里的分层是同一种思路。**
    就像 `SummaryPolicy` 不直接等于摘要算法，`Summarizer` 单独抽出来负责“怎么生成摘要”；这里也是一样，`MultiLevelMemory` 不直接等于记忆更新算法，`MemoryUpdater` 单独抽出来负责“怎么生成新记忆”。

  - **这样做更容易替换不同更新方式。**
    当前实现是 `LLMMemoryUpdater`，但后面完全可能换成规则式 updater、更便宜的小模型 updater、结构化 schema updater、检索增强 updater。如果更新逻辑写死在 `MultiLevelMemory` 里，每换一种方式都要改 memory 主体本身。

  - **测试和演进边界也会更清晰。**
    拆开之后可以分别测试“记忆状态是否正确持有和存储”与“更新逻辑是否正确抽取和改写”。不然你会把存储问题和生成问题绑在一起测，后面演进时也更难替换某一层能力。

### Q5. [重点] `ch06` 如何区分“本轮上下文”和“长期记忆”？

- **一句总结：**
  `ch06` 用“上下文引擎 + policy”管理本轮消息，用“memory 子系统 + 持久化存储”管理长期知识；前者服务当前推理，后者服务未来会话。

- **详细回答：**
  `ch06` 靠三层边界来区分本轮上下文和长期记忆。

  - **第一层是生命周期边界。**
    本轮上下文只服务当前这次或当前这几轮推理，核心是“这次请求发给模型时带哪些消息”；长期记忆跨会话存在，哪怕 TUI 重启、上下文清空，记忆仍然保留。

  - **第二层是数据载体边界。**
    本轮上下文在 `context.Engine` 里，主要是 `messages` 和 turn draft；长期记忆在 `memory.MultiLevelMemory` 里，核心是 `MemoryContent`，并持久化到 `~/.babyagent/memory/MEMORY.md` 和 `{workspace}/.babyagent/memory/MEMORY.md`。

  - **第三层是处理方式边界。**
    本轮上下文通过 `truncate / offload / summarize` 这些 policy 做治理，目标是控制窗口预算；长期记忆通过 `MemoryUpdater.Update(oldMemory, newMessages)` 从新消息里提取值得长期保留的信息，目标是沉淀跨会话知识。

  更具体地说，`ch06` 的流程是：一轮对话先进入 `context.Engine`；当前请求用的是 system prompt 和当前上下文消息；这一轮结束后，`CommitTurn()` 才调用 `memory.Update(...)`；记忆被更新并持久化；下一轮请求时，再通过 `BuildSystemPrompt()` 把记忆注入回来。

  这里 `CommitTurn()` 的角色也值得单独看清楚，因为它同时站在“上下文提交”和“记忆更新”的分界点上，但两者的判断方式并不一样。

  - **对本轮上下文来说，`CommitTurn()` 是正式入账点。**
    只要这一轮完整成功，`draft.NewMessages` 就会被写进 `Engine.messages`。也就是说，进入正式上下文的判断标准是：这轮消息是不是已经成为真实发生过的稳定历史。它不是在判断“值不值得长期保留”，而是在判断“这轮消息是否有资格成为正式历史”。

  - **对长期记忆来说，`CommitTurn()` 不是最终判断器，只是触发更新的时机。**
    `CommitTurn()` 会把本轮新增消息传给 `memory.Update(...)`，但它并不自己决定“哪些内容应该进入长期记忆”。真正的筛选和改写逻辑在 `MemoryUpdater` 里。也就是说，`CommitTurn()` 负责把“这轮稳定发生过的消息”交给 memory 子系统，而不是亲自判断每条消息值不值得沉淀。

  - **所以两条链路的判断标准不同。**
    进入本轮正式上下文，看的是真实性和完整性：这轮是否成功完成、消息是否已成为稳定历史。进入长期记忆，看的则是长期价值：这些稳定历史里，哪些信息值得跨会话继续保留。

  这也是为什么 `CommitTurn()` 之后还要再走一次 `memory.Update(...)`。先解决“这轮消息是否应该成为正式历史”，再解决“这段正式历史里哪些东西值得升格成长期记忆”，两者不是同一个判断。

  所以它们不是一份数据的两种名字，而是两套系统。上下文是当前在线工作记忆，长期记忆是跨会话沉淀知识。

### Q6. [重点] 为什么记忆更新要在 `CommitTurn` 之后做，而不是边对话边写 `memory`？

- **一句总结：**
  记忆更新放在 `CommitTurn` 之后，是因为长期记忆应该基于“一轮已经稳定完成的结果”来沉淀，而不是基于执行中的半成品；这样才能避免把中途失败、被取消或语义未闭合的信息写进长期记忆。

- **详细回答：**
  这个设计和 `ch05` 里“policy 为什么放在整轮结束后”其实是同一类边界问题。区别在于，`policy` 处理的是当前上下文，`memory` 处理的是跨会话知识，所以对稳定性的要求更高。

  可以分几层看。

  - **长期记忆不该建立在半成品上。**
    一轮对话里，模型可能先输出一段 reasoning，然后决定调 tool，tool 返回结果后再继续修正判断。如果你边对话边写 memory，就有可能把“中途推断”“未完成结论”甚至错误方向先写进长期记忆。这样污染会比污染当前上下文更严重，因为它会跨会话持续存在。

  - **只有整轮结束后，语义链才真正闭合。**
    一轮完整交互通常是：user 提需求，assistant 做判断，必要时调 tool，tool 返回结果，assistant 再给出最终回答。只有走完整条链，你才更有资格判断“这一轮真正值得沉淀的是什么”。如果中途就更新 memory，系统拿到的只是局部状态，不是最终事实。

  - **这和 turn draft / commit 机制是配套的。**
    `ch05` 已经把“草稿状态”和“正式上下文”分开了。`ch06` 继续沿用这条边界：先让本轮消息在 `draft` 和当前执行链里跑完，等 `CommitTurn()` 时再把它们视为正式输入。然后 memory 更新再基于这批“已经被正式接纳”的消息进行。这种顺序保证 memory 和正式上下文站在同一个稳定边界上。

  - **如果中途写 memory，回滚会变得非常麻烦。**
    当前 `AbortTurn()` 可以是 no-op，一个重要原因就是草稿还没污染正式状态。如果 memory 也在执行中被更新了，那一轮失败时你就不仅要回滚上下文，还要回滚 global memory、workspace memory，以及已经写进文件系统的持久化内容。这会把系统复杂度直接拉高一层。

  - **长期记忆的抽取更适合用“本轮新增消息”作为完整输入。**
    现在 `CommitTurn()` 里把 `draft.NewMessages` 作为 memory updater 的输入，这样 updater 看到的是一轮已经结束后真正发生过的消息集合。这个输入比流式增量更适合做“提取用户偏好、项目知识、长期模式”这种任务，因为它已经有完整上下文，而不是碎片。

  - **这也是一种可靠性优先的工程选择。**
    memory 一旦写错，不像当前上下文那样下一轮就自然被覆盖，它可能长期影响系统判断。所以这章刻意选择保守路线：宁可晚一点写，也不要早一点把不稳定信息沉淀进去。

  所以更准确地说，memory update 放在 `CommitTurn()` 之后，不是实现顺手，而是在明确一条原则：只有当一轮消息已经成为正式历史后，它才有资格参与长期记忆更新。

- **流程图：**

```text
[用户输入]：query
        |
        v
[StartTurn]：创建 TurnDraft，保存本轮草稿消息
        |
        v
[BuildRequestMessages]：取 system prompt + 稳定上下文消息
        |
        v
[Agent]：追加 draft.NewMessages，发起本轮 LLM / tool loop
        |
        v
[判断]：本轮是否完整成功？
  |                           |
  | 是                        | 否
  v                           v
[CommitTurn]：把 draft.NewMessages 写入 Engine.messages
                              [AbortTurn]：丢弃草稿，
  |                           不污染正式上下文，也不更新 memory
  v
[recountTokens]：重算上下文 token
  |
  v
[applyPolicies]：执行 truncate / offload / summarize
  |
  v
[Memory.Update]：把“旧记忆 + 本轮新消息”交给 MemoryUpdater
  |
  v
[LLMMemoryUpdater]：调用后台模型生成新的 Global / Workspace Memory
  |
  v
[Storage.Store]：写入
  - ~/.babyagent/memory/MEMORY.md
  - {workspace}/.babyagent/memory/MEMORY.md
  |
  v
[BuildSystemPrompt]：下一轮请求时把 memory 注入 system prompt
```

### Q7. 为什么当前 memory update 只看 `draft.NewMessages`，而不是重新看完整上下文？

- **一句总结：**
  当前只把 `draft.NewMessages` 交给 memory updater，是为了让记忆更新聚焦“本轮新增事实”，避免每轮重复扫描完整上下文带来的成本、噪声和重复改写；完整上下文已经通过旧 memory 间接参与了更新。

- **详细回答：**
  这个设计的核心不是“完整上下文不重要”，而是 memory update 要有一个清晰的输入边界。`CommitTurn()` 发生时，系统已经有两类信息：一类是历史上已经沉淀过的 `memory`，一类是本轮刚刚稳定完成的 `draft.NewMessages`。当前实现选择把这两者组合起来，而不是重新把整个 `Engine.messages` 都交给 updater。

  更准确地说，`LLMMemoryUpdater` 看到的并不是孤立的新消息。它的输入是“旧记忆 + 本轮新消息”。旧记忆代表过去已经被压缩、筛选、沉淀过的长期信息；本轮新消息代表这次对话刚刚新增、还没有被判断是否值得长期化的信息。所以它不是完全不看历史，而是不重新扫描全部原始历史。

  这样做有几个原因。

  - **避免重复处理历史消息。**
    如果每轮都重新看完整上下文，那么同一批历史消息会被反复送进 updater。模型可能每次都重新解释一遍旧内容，导致旧记忆被不断无意义改写，甚至出现轻微漂移。

  - **降低成本。**
    完整上下文会越来越长，尤其前面章节已经引入 tool result、summary、offload。每次 memory update 都重新喂完整上下文，token 成本会迅速膨胀。只看本轮新增消息，可以把更新成本控制在“增量更新”的尺度。

  - **降低噪声。**
    完整上下文里有大量临时讨论、试错过程、工具输出、被摘要过的信息。memory updater 的任务不是重建整段对话，而是判断“本轮新增内容里有没有值得长期保留的东西”。输入越大，模型越容易被低价值历史干扰。

  - **让职责边界更清楚。**
    `context.Engine` 负责维护当前会话历史，`MemoryUpdater` 负责把新增稳定消息抽取成长期记忆。如果 updater 每次都重新读完整上下文，它就会变成另一个上下文治理器，和 `context.Engine`、summary policy 的职责重叠。

  - **避免和 summarize / truncate / offload 的结果互相打架。**
    到了 `ch05` 之后，完整上下文本身可能已经被摘要、截断、卸载过。重新看完整上下文并不一定等于看到了完整事实，反而可能让 updater 把被压缩后的表述再次压缩，产生二次摘要误差。

  这里还要注意，`draft.NewMessages` 不是只包含用户的 query。它更准确地说是“本轮新增消息集合”，通常会包含这一轮用户输入、模型回复、可能的 tool call、tool result，以及工具执行后的最终回答。

```text
用户输入
-> 追加 user message 到 draft.NewMessages
-> 模型回复
-> 追加 assistant message 到 draft.NewMessages
-> 如果有 tool call
   -> 追加 assistant tool_call message
   -> 追加 tool result message
   -> 再追加后续 assistant answer
-> CommitTurn()
-> 把 draft.NewMessages 写入 Engine.messages
-> memory.Update(draft.NewMessages)
```

  这也是为什么它适合作为 memory update 的输入：它不是只看用户说了什么，也能看到模型最终怎么理解、工具返回了什么、本轮结论是什么。

  但这里也有风险。既然 `draft.NewMessages` 里可能包含 assistant 的推断、tool 的临时结果和中间过程，`MemoryUpdater` 就必须区分用户明确说出的事实、工具验证过的事实、模型自己的推断、临时过程信息和最终稳定结论。否则系统就容易把模型脑补、临时 tool 输出、半成品结论写进长期记忆。

  当然，这个设计也有代价。只看 `draft.NewMessages`，意味着 updater 对“本轮消息和很早之前某个细节之间的关系”不一定敏感。如果旧 memory 没有保留那个细节，而完整上下文里还残留着它，当前 updater 可能看不到。因此更成熟的系统通常会在“只看新增消息”和“必要时检索相关历史”之间折中。

  一个更工业化的方案可能是：默认只用旧 memory + 本轮新消息做增量更新；如果本轮涉及纠错、冲突、长期计划、项目关键事实，再按需检索相关历史片段；如果发现旧 memory 和新消息冲突，再进入专门的冲突处理流程。这样既保留增量更新的成本优势，也不会完全丢掉历史关联能力。

  所以当前 `ch06` 的做法可以理解为教学版的增量 memory update：它不是最完整的记忆更新策略，但它很清楚地表达了一个重要原则：长期记忆更新应该优先关注“这轮新增了什么”，而不是每轮重新理解整个世界。

### Q8. [重点] `memory` 作为 system prompt 的原因是什么？system prompt 里还有什么？

- **一句总结：**
  `memory` 放进 system prompt，是因为它在当前实现里被视为“每轮都应稳定可见的长期背景知识”；而当前 system prompt 里除了 memory，还承载 Agent 身份、运行环境、workspace 信息和高优先级行为规则。

- **详细回答：**
  `memory` 放进 `system prompt`，本质上是因为它在当前实现里被当成高优先级、每轮都应稳定可见的背景约束，而不是普通对话消息。

  可以分两部分看。

  - **为什么 `memory` 要作为 system prompt 注入。**
    `memory` 本质上是背景知识，不是本轮对话内容。它描述的是用户长期偏好、当前工作区知识、跨会话沉淀出来的稳定事实。这些内容更像“模型在这轮开始前就应该知道的背景”，而不是这轮对话里新发生的一条消息。

    放进 system prompt，能保证每轮稳定生效。如果把 memory 当普通 `user` / `assistant` 消息混进消息流，它会和对话历史一起被截断、摘要、外置。但 memory 的目标恰恰是“跨会话稳定存在”，所以更适合作为每轮请求重新注入的固定背景层。

    这也更容易和上下文工程分层。当前消息链负责本轮上下文；memory 作为 system prompt 负责长期背景。这样可以明确区分“本轮发生了什么”和“模型在开始这轮前已经知道什么”。

  - **memory 变化后，不需要刷新历史里的 system prompt。**
    `ch06` 里 system prompt 不是作为一条固定消息长期存进 `Engine.messages`，而是在每次请求前通过 `BuildRequestMessages()` 动态构造。`BuildRequestMessages()` 会调用 `BuildSystemPrompt()`，而 `BuildSystemPrompt()` 会读取当前最新的 `memory.String()`。所以 memory 更新完成后，下一轮请求自然会拿到新的 system prompt，不需要回头修改历史消息。

    这点很关键。如果 system prompt 被当成普通历史消息 append 进上下文，那确实会出现“旧 system prompt 没刷新”的问题。但当前实现没有这么做，`Engine.messages` 保存的是正式历史消息，system prompt 是每轮临时 prepend 的动态背景层。

  - **system prompt 里除了 memory 还有什么。**
    看 `ch06/prompt.go` 和 `ch06/context/engine.go`，当前 system prompt 里主要有四类东西：第一类是 Agent 身份，比如 `You are BabyAgent, a helpful coding assistant.`；第二类是运行环境信息，比如 `{runtime}`；第三类是 workspace 信息，比如 `{workspace_path}`；第四类才是 `{memory}`，它会展开成 `Global Memory` 和 `Workspace Memory`。除此之外，system prompt 里还有一组高优先级行为规则，比如调工具前先说明意图、不要预测工具结果、修改文件前先读、工具失败先分析再重试、需求模糊时先澄清。

  所以更准确地说，当前 system prompt 由四类东西组成：身份设定、环境信息、长期记忆、行为规则。`memory` 放进这里，是因为它和这些内容一样，都属于模型开始工作前应稳定知道的背景层。

- **Memory.Update 内部流程图：**

  - GlobalMemory
  - WorkspaceMemory

### Q9. 长期记忆和 system prompt 绑定后，会不会反过来污染主模型行为？

- **一句总结：**
  会有这个风险；把 memory 放进 system prompt 会提高它的稳定性和优先级，但如果记忆错误、过时、过宽泛或包含不该保存的信息，也会更稳定地影响主模型行为，所以 memory 注入必须配合边界、可信度和纠错机制。

- **详细回答：**
  会，而且这是长期记忆系统最核心的风险之一。`system prompt` 不是普通上下文，它通常比普通 `user / assistant` 消息更靠前、更稳定，也更像模型本轮工作的背景约束。把 memory 放进这里，等于告诉模型：这些长期信息是你开始回答前应该知道的背景。

  这带来好处，也带来副作用。好处是用户偏好、项目知识、长期约定可以稳定生效，不会轻易被普通上下文裁剪掉。副作用是，一旦 memory 里有错误信息，它也会以更高优先级、更稳定的方式影响后续所有回答。

  可以从几类污染看。

  - **错误事实污染。**
    如果 memory 错把模型推断写成事实，比如“这个项目使用 React”，但项目实际不是这样，那么后续模型每次看到 system prompt 都可能沿着错误事实继续推理。

  - **过时信息污染。**
    项目技术栈、运行命令、用户偏好都可能变化。如果旧记忆没有被替换或降权，它会继续影响新会话，甚至压过用户当前的真实意图。

  - **过度泛化污染。**
    一次局部偏好如果被写成全局偏好，就会影响过宽。比如用户在某一章说“回答精简一点”，如果被记成全局长期风格，后面需要详细学习资料时就可能反而影响质量。

  - **行为规则污染。**
    如果 memory 里混入了类似“以后不要运行测试”“总是直接修改文件”这种行为约束，它就不再只是背景事实，而是在改变 Agent 的行为策略。这类内容尤其危险，因为它会和真正的 system instruction 发生竞争。

  - **敏感信息污染。**
    如果长期记忆保存了不该保存的 token、密钥、隐私信息，放进 system prompt 后就会在后续请求里反复出现，增加泄露面。

  所以长期记忆不能只是“写进去，然后每轮全量注入”。更稳的做法应该是给 memory 设边界。

  - **记忆内容要分级。**
    用户偏好、项目事实、临时任务状态、敏感信息、行为约束不应该混在同一层里。尤其是行为约束类内容，不应该随便进入长期记忆。

  - **记忆需要来源和时间。**
    生产系统里更适合给每条 memory item 标注来源、时间、更新时间、置信度和作用域。这样模型或系统才能判断它是不是仍然可信。

  - **注入时要按需选择。**
    当前 `ch06` 是全量注入 `Global / Workspace`，教学上简单，但工业系统更常见的是按当前任务检索相关 memory，再注入必要片段，避免无关记忆污染当前推理。

  - **用户纠正要有最高优先级。**
    如果用户明确说“不是这样”“以后不要记这个”“这个项目已经改了”，系统应该覆盖、删除或降权旧记忆，而不是把新旧说法并列保留。

  - **system prompt 里要明确 memory 的地位。**
    可以告诉模型：memory 是历史背景，不是绝对真理；如果 memory 和用户当前明确指令、工具结果、代码事实冲突，应以当前用户指令和可验证事实为准。

  所以，把 memory 绑定到 system prompt 本身不是错，它是最简单有效的注入方式。但这也意味着 memory 不再只是一个被动存储，而是会主动塑造主模型行为。记忆系统越强，越需要配套治理：写入过滤、作用域控制、按需召回、冲突处理、用户纠错、敏感信息保护。否则它确实会把错误和过时信息放大成长期行为偏差。

### Q10. [重点] 为什么记忆更新要走后台模型，而不是直接用前台主模型顺手更新？

- **一句总结：**
  记忆更新走后台模型，是因为它和主对话不是同一种任务：前台模型负责完成当前交互，后台模型负责低成本地抽取和整理长期记忆；拆开后成本、职责、失败边界和后续演进都会更清楚。

- **详细回答：**
  因为“和用户对话”与“抽取长期记忆”其实是两种不同任务，放在同一个主模型链路里做，成本、稳定性和职责都会混在一起。所以 `ch06` 用后台模型来做 memory update，本质上是在把“主任务执行”和“后台知识整理”拆开。

  可以从几个角度看。

  - **前台模型和后台模型的任务目标不同。**
    前台模型负责回答用户、调 tool、推进当前任务；后台模型负责读本轮新消息、判断哪些信息值得长期保留、把它们整理成新的 Global / Workspace Memory。这两者虽然都在用 LLM，但不是同一种工作负载。

  - **记忆更新通常不需要最强的大模型。**
    当前主模型可能是为了更强 reasoning、更稳 tool use、更大上下文；但 memory update 更像一个“抽取 + 重写”任务，很多时候用一个更便宜、更轻的模型就够了。所以拆成后台模型，最直接的好处就是控制成本。

  - **把 memory update 从前台主链路里拆出去，更容易单独演进。**
    后面你可能会想调整 memory update 的 prompt、使用的模型、更新频率、是否做异步更新、是否只在某些轮次更新。如果它和前台模型绑死，后续任何改动都会影响主对话链路。

  - **这也是一种职责分离。**
    前台模型是“和用户一起完成任务”的 worker；后台模型更像“帮系统整理和沉淀知识”的 maintenance worker。这两种职责拆开后，系统结构会更清楚。

  - **对失败隔离也更友好。**
    如果 memory update 失败，你不一定希望主对话本身也受太大影响。独立后台模型后，系统更容易做到“前台回答完成了，但后台记忆更新失败，只记日志或降级处理”。这比把两者绑在一个调用里更容易控制失败边界。

  - **这也是更接近真实系统的做法。**
    工业系统里，主用户请求链路和后台整理链路本来就经常分开：主链路追求响应质量和交互体验，后台链路追求成本、吞吐、稳定性和异步处理能力。`ch06` 用前台 / 后台模型分工，其实已经是在往这种系统形态靠。

  所以更准确地说，记忆更新走后台模型，不只是“省钱”，而是在明确：memory update 是后台知识整理任务，不应该和前台主对话任务混成同一条模型职责链。

  如果对照 ChatGPT 这类产品，需要注意公开信息和工程推断的边界。OpenAI Help Center 公开说明里，ChatGPT memory 主要有两类：`Saved memories` 和 `Reference chat history`。`Saved memories` 类似 custom instructions，会作为生成回答时使用的上下文；ChatGPT 也可以自动更新、合并、删除这些 saved memories。`Reference chat history` 则表示 ChatGPT 可以参考过去对话中的有用信息，但不会记住每个细节，这些信息也会随时间变化。

  但官方没有公开说“是不是一个后台模型专门负责 memory update”。所以不能严谨地说 GPT / ChatGPT 的实现一定也是后台模型。更稳的判断是：`ch06` 采用“后台模型更新 memory”是一种清晰的工程拆分；ChatGPT 官方公开的是 memory 会被自动保存、更新和引用，但没有公开底层一定由后台模型完成。

  从生产系统角度看，你提到的“多轮或有条件才触发 memory”更接近真实工程形态。生产系统通常不会简单每轮同步完整重写 memory，而是会先判断本轮是否有记忆价值；当用户明确说 “remember this” 时强触发；普通对话可能按事件、阈值、会话结束或后台任务触发；记忆更新也通常会和主回答链路解耦，避免拖慢用户响应。

  参考资料：
  - https://help.openai.com/en/articles/8983136-what-is-memory
  - https://help.openai.com/en/articles/11146739-how-does-reference-saved-memories-work

### Q11. [重点] 为什么 `LLMMemoryUpdater` 现在用“旧记忆 + 新消息 -> 生成整份新记忆”的方式，而不是只输出 patch / diff？

- **一句总结：**
  当前用整份重写而不是 patch / diff，是因为对 Markdown 文本记忆来说，完整重写更符合 LLM 能力边界，也更容易保证状态闭合；而 patch / diff 需要额外的结构化编辑协议，这超出了本章的复杂度目标。

- **详细回答：**
  因为当前这章优先追求的是实现简单、状态闭合、容易落地，而不是最细粒度的记忆编辑协议。让模型直接输出“整份新记忆”，本质上是在把 memory update 设计成一次重写结果，而不是一次增量补丁操作。

  可以从几个角度看。

  - **整份重写更容易保证最终状态自洽。**
    如果只输出 patch / diff，系统还要再解决：patch 怎么应用、应用顺序是什么、多个 patch 冲突怎么办、删改同一条记忆怎么处理。而整份新记忆的方式很直接：模型给出“更新后的最终版本”，系统直接替换掉旧版本即可。这样状态闭合最简单。

  - **当前记忆内容本来就是 Markdown 文本，不是结构化对象。**
    现在的 `GlobalMemory` 和 `WorkspaceMemory` 本质上都是一段 Markdown 字符串。对这种自由文本来说，patch / diff 没有天然稳定的语义边界。模型很难可靠地产出类似“删除第 3 条 bullet”或“修改某一节标题下的第二行”这种可精确执行的补丁。所以对自由文本，直接重写整份结果通常比生成 patch 更稳。

  - **LLM 更擅长“给出改写后的完整文本”，不擅长“生成严格可执行补丁”。**
    让模型做“基于旧记忆和新消息，输出新的完整记忆”，通常比让它做“只输出最小变更补丁，并保证可正确应用”更符合 LLM 的自然能力边界。

    原因在于，完整改写主要是语义生成任务：模型只要理解旧记忆、新消息和目标格式，然后产出一份自洽的新文本即可。它不需要精确指出“原文第几条、第几行、第几个字符应该怎么改”。

    严格 patch / diff 则更像可执行编辑协议。模型不仅要判断语义上该改什么，还要稳定定位旧内容中的目标片段，输出可机器应用的操作，例如新增、删除、替换某个具体条目。只要定位不准、上下文片段不完全匹配、或者补丁顺序有问题，patch 就可能应用失败，甚至错误修改无关内容。

    对当前这种 Markdown 自由文本记忆来说，这个问题更明显。Markdown 里一条记忆没有稳定 ID，也没有结构化字段边界。模型说“修改用户偏好里的第二条”并不一定能被程序可靠执行。除非先把 memory 设计成结构化条目，并给每条记忆稳定 ID、来源、版本和操作 schema，否则 patch / diff 会比完整重写脆弱得多。

  - **当前实现想把系统复杂度压低。**
    如果走 patch / diff 路线，除了模型输出，你还需要额外实现 patch schema、patch validator、patch applier、冲突处理、回滚逻辑。这会让 `ch06` 从“基础 memory system”直接跳到“结构化记忆编辑系统”，复杂度会上一个台阶。

  - **整份重写更容易和持久化存储对接。**
    当前存储后端就是简单的文件存储。直接写整份新内容：`Store(key, newMemory)` 就结束了。如果是 patch / diff，还要决定是先读旧文件再应用 patch，还是存 patch 日志，以及失败时怎么恢复。这都不是本章当前想引入的复杂度。

  - **这也暴露了当前实现的代价。**
    整份重写虽然简单，但也有明显缺点：小改动也要重写整份内容、更容易因为一次更新把无关内容改坏、不容易追踪“到底改了哪几处”、更难做细粒度冲突解决。所以后面如果系统继续升级，走向 patch / diff 或结构化 memory update 是很自然的下一步。

  所以更准确地说，`LLMMemoryUpdater` 现在选择“旧记忆 + 新消息 -> 生成整份新记忆”，是因为当前记忆是自由文本，系统优先追求最终状态简单、自洽、易存储、易实现；patch / diff 虽然更精细，但会引入额外的编辑协议和冲突处理复杂度。

### Q12. 为什么 `LLMMemoryUpdater` 现在用 XML 标签包裹输出，而不是 JSON？

- **一句总结：**
  这里用 XML 而不是 JSON，是因为当前输出是两段自由 Markdown 文本，XML 标签更适合做轻量包裹和提取，能降低模型在长文本场景下的格式出错成本。

- **详细回答：**
  因为当前这章要解决的是：让模型稳定地产出两段长文本记忆，而不是产出一个严格结构化的数据对象。在这种场景里，XML 标签比 JSON 更宽松，也更适合包裹 Markdown 大段文本。

  可以分几层看。

  - **当前输出内容本质上是“长文本块”，不是细粒度字段对象。**
    `GlobalMemory` 和 `WorkspaceMemory` 最终都是 Markdown 字符串，不是很多小字段组成的结构化记录。让模型输出 `<global>...</global>` 和 `<workspace>...</workspace>`，本质上是在说“给我两块完整文本”。这和 JSON 那种“字段值必须严格转义、结构必须合法闭合”的要求不一样。

  - **XML 标签更适合包裹自由文本。**
    这里每一段 memory 里可能包含 Markdown 标题、bullet list、代码块、反引号、冒号、引号。如果用 JSON，模型就必须同时满足两件事：内容语义正确，JSON 转义和格式也严格正确。这会提高出错概率。XML 标签方式更接近“用边界标记包裹一段文本”，对模型更宽松。

  - **当前解析需求很简单，只需要提取两个块。**
    现在系统根本不需要一个通用 JSON parser 去理解复杂 schema，它只需要找到 `<global>...</global>` 和 `<workspace>...</workspace>`。所以用正则提取这两个块就够了。这和“我要解析几十个字段、做严格类型校验”的场景完全不是一个复杂度。

  - **这是一种工程上的“最小结构化”。**
    它不是完全无结构的纯文本，因为至少有两个稳定边界；但也不是强结构化对象，因为里面的正文仍然是自由 Markdown。所以 XML 在这里更像一个轻量容器格式。

  - **JSON 在这章不是不能用，而是收益没那么大。**
    如果现在要求模型输出 `{\"global_memory\":\"...\",\"workspace_memory\":\"...\"}`，理论上当然也行。但你实际得到的收益只是字段名更标准，代价却是更容易因为引号、换行、转义导致解析失败，模型必须同时满足文本内容和 JSON 语法正确性，对当前这种“长文本块输出”帮助有限。

  - **这也说明当前实现仍然是偏教学和实用折中的。**
    更工业化的系统里，后面如果 memory 变成结构化条目、带类型和元数据、可做 patch / diff、可做冲突解决，那时候转向 JSON 或更严格 schema 就会更自然。但 `ch06` 当前还停留在“生成两段 Markdown 记忆文本”的阶段，XML 标签已经够用了。

  所以更准确地说，`LLMMemoryUpdater` 现在用 XML 标签，不是因为 XML 更现代，而是因为它更适合当前这种“从模型拿两块长 Markdown 文本，并做轻量边界提取”的需求。

### Q13. 为什么 `LLMMemoryUpdater` 当前没有做冲突检测和记忆纠错？

- **一句总结：**
  当前没有做冲突检测和记忆纠错，是因为 `ch06` 先解决“记忆能不能形成闭环”，还没进入“记忆是否可信、冲突怎么治理”的阶段；后者需要结构化条目、来源、时间和优先级规则，不是当前自由文本 memory 能轻量承载的。

- **详细回答：**
  因为 `ch06` 这一章的目标还是先把“记忆能写进去、能跨会话保留、能被下一轮读到”这条最小闭环跑通，还没进入“记忆可信度治理”那一层。更准确地说，冲突检测和记忆纠错不是一个小补丁，而是会把系统复杂度明显抬高的一整层能力。

  可以分几层看。

  - **当前实现把 memory update 当成“重写结果”，不是“受约束的知识编辑”。**
    现在 `LLMMemoryUpdater` 的工作方式是：给它旧记忆，给它新消息，让它输出新的整份 `Global / Workspace Memory`。这种模式的重点是先完成“更新”，而不是先完成“冲突求解”。一旦要做冲突检测，你就不能只看最终新文本，还得知道哪条记忆和哪条新消息冲突、旧记忆为什么被覆盖、是更新、修正，还是误提取。

  - **当前 memory 还是自由 Markdown 文本，不是结构化知识条目。**
    冲突检测最容易建立在结构化表示上，比如 key-value、带时间戳的事实条目、带来源和置信度的 memory item。但 `ch06` 现在存的是两段 Markdown。对这种自由文本，要可靠做冲突检测会很难，因为系统甚至不清楚“哪一段是一个独立事实单元”。

  - **纠错需要来源、优先级和版本语义，当前都还没有。**
    真正的记忆纠错通常至少要回答：新消息和旧记忆冲突时信谁、用户明确纠正和模型推断哪个优先、最近事实和长期偏好冲突怎么办、是覆盖旧记忆还是并存两个版本。这些都属于 memory governance。当前 `ch06` 还没有来源标记、置信度、时间戳、版本控制、冲突解决规则。

  - **这章优先级是“可用闭环”，不是“高可信闭环”。**
    当前系统已经完成了记忆提取、记忆持久化、记忆注入，这是第一步。冲突检测和纠错属于第二步，它建立在“memory 已经存在且开始产生副作用”之后，才值得引入。

  - **这也反映了教学实现和工业实现的差距。**
    工业系统里，记忆一旦长期存在，就必须关心错误记忆固化、过时记忆覆盖新事实、用户明确纠正后的优先级、多轮抽取导致的漂移。但这些问题的前提是：你已经把 memory 当成一个需要治理的知识库，而不只是一个能工作的持久化文本。

  所以更准确地说，`LLMMemoryUpdater` 当前没有做冲突检测和记忆纠错，不是因为这件事不重要，而是因为 `ch06` 还停在“先建立长期记忆闭环”的阶段；冲突检测、来源管理、版本和纠错属于下一层 memory governance 能力。

### Q14. 为什么 `memory.String()` 现在把 Global / Workspace 全量注入，而不是按需检索后再注入？

- **一句总结：**
  当前全量注入，是为了先用最简单的方式打通长期记忆闭环；按需检索更高级，但它要求 memory 先变成结构化、可索引、可召回的系统，这超出了 `ch06` 的复杂度目标。

- **详细回答：**
  因为 `ch06` 这一章实现的是最小可用的长期记忆闭环，不是完整的检索式 memory system。全量注入虽然粗，但实现最简单，也最容易保证“记忆真的被模型看见了”。

  可以分几层看。

  - **当前目标是先打通“记忆写入 -> 持久化 -> 再次注入”的闭环。**
    这一章先要证明三件事：记忆能被提取出来、记忆能跨会话保存、下一轮请求时模型真的能用到它。全量注入是最直接的方式，因为不需要再引入“检索是否命中”的不确定性。

  - **当前 memory 还是两段自由 Markdown 文本，不是可检索条目集合。**
    现在的 `GlobalMemory` 和 `WorkspaceMemory` 本质上是两大段文本。这种表示方式天然更适合“整体注入”，不适合“按条召回”，因为系统还没有独立 memory item、embedding、metadata、relevance scoring。

  - **按需检索会把系统复杂度抬到下一层。**
    一旦改成检索式注入，你就得额外解决：memory 如何切片、如何建立索引、当前 query 如何做检索、召回 Top-K 的依据是什么、检索不到时怎么办、检索错了会不会漏掉关键背景。这已经不是“简单注入方式不同”，而是 memory architecture 变化。

  - **全量注入更适合教学阶段观察效果。**
    你现在很容易验证：memory 文件写了什么、`memory.String()` 里有什么、system prompt 注入了什么、下一轮模型为什么会记得。如果中间再插一层 retrieval，学习主线会被打散。

  - **这也说明当前实现的代价。**
    全量注入虽然简单，但明显不够经济：memory 变大后会占更多 token、噪声会增加、不相关记忆也会一起进入 prompt，后面很容易逼近“memory 本身又需要被治理”这个问题。所以后面系统继续升级时，走向“结构化 memory + 按需检索注入”是很自然的。

  所以更准确地说，`memory.String()` 现在全量注入，不是因为这是最优方案，而是因为 `ch06` 先追求最小可用闭环；按需检索需要 memory 从“文本块”升级成“可检索知识库”，那已经是下一阶段的系统形态。

### Q15. `LLMMemoryUpdater` 里的 prompt 是否是在扮演 memory gatekeeper？

- **一句总结：**
  是的，`updateMemoryPrompt` 本质上就是一个基础版 memory gatekeeper：它告诉后台模型如何从旧记忆和新消息里提取长期价值信息，但当前写入门槛还偏宽，不能单靠它保证记忆质量。

- **详细回答：**
  `ch06` 里确实有一个专门的 prompt 在负责 memory 总结和更新过程，对应代码在 `ch06/memory/update.go` 的 `updateMemoryPrompt`。它不是让模型继续回答用户，而是把模型放到“memory management system”的角色里，让它分析当前记忆和新消息，然后生成新的 `Global Memory` 和 `Workspace Memory`。

  可以从几个角度看。

  - **它定义了后台模型的角色。**
    prompt 开头写的是 `You are a memory management system for an AI coding assistant.` 这相当于告诉模型：你现在不是对话助手，而是在做记忆管理。这是 gatekeeper 的第一层，因为它改变了模型处理输入的任务目标。

  - **它同时输入旧记忆和新消息。**
    prompt 里有 `{current_memory}` 和 `{new_messages}`。这意味着更新不是只看本轮消息，而是要结合已有记忆判断应该保留、更新、删除或维持什么内容。

  - **它定义了 Global / Workspace 的边界。**
    prompt 明确告诉模型：`Global Memory` 记录用户偏好、长期模式、背景信息；`Workspace Memory` 记录项目结构、技术栈、构建命令、项目约定等。这是在约束“什么信息应该写到哪一层”。

  - **它给出了基础写入原则。**
    当前 prompt 已经要求 concise、preserve existing important information、remove outdated or superseded information，也要求只更新受影响的 memory level。这些都是基础的 gatekeeping 规则。

  - **但它的写入门槛还不够强。**
    你说的“memory 需要沉淀重要且有长期价值的信息”是更准确的标准。当前 prompt 虽然提到了长期模式和项目知识，但还没有足够明确地禁止临时任务状态、未验证推断、一次性中间结论、敏感信息进入 memory。所以它是一个基础版 gatekeeper，不是生产级 gatekeeper。

  所以更准确地说，`updateMemoryPrompt` 已经承担了“总结本轮并判断是否更新长期记忆”的角色，但它仍然主要靠提示词约束模型行为。后面如果要更可靠，需要配合结构化校验、写入门槛、来源标记和失败回退。

### Q16. 既然 memory 更新靠 prompt，工程上怎么保证输出一定合法？

- **一句总结：**
  当前实现靠 prompt 工程让模型尽量输出合法 XML，但 prompt 本身不能提供工程保证；真正可靠的做法是结构化输出、解析校验、失败回退、必要时重试修复。

- **详细回答：**
  这里确实是在用提示词工程。`updateMemoryPrompt` 会约束模型角色、输入、输出格式，并要求模型返回 `<global>...</global>` 和 `<workspace>...</workspace>`。随后代码用 `extractXMLTag()` 从返回文本里正则提取两段内容。

  这是一种轻量方案，适合教学和 demo，但不是强保证。

  - **prompt 只能提高格式正确概率，不能保证合法。**
    模型不是编译器。即使 prompt 写了格式要求，它仍然可能漏掉 `<global>` 或 `<workspace>`，也可能标签写错、标签嵌套异常、在标签外输出解释文字、输出空内容，或者因为响应截断导致 XML 不完整。

  - **当前解析方式也比较脆弱。**
    `extractXMLTag()` 提取不到标签时会返回空字符串。如果没有进一步校验，系统就可能把某一层 memory 写空。这说明 prompt + regex 只是最小可用路径，不是可靠边界。

  - **更稳的工程做法是结构化输出。**
    如果模型 API 支持 strict JSON schema，可以要求模型输出 `global_memory` 和 `workspace_memory` 两个字段，并由 API 或 SDK 做结构校验。这比纯 prompt + 正则稳很多。

  - **解析后还需要校验。**
    即使用 XML 或 JSON，也应该检查 global / workspace 是否都存在、是否异常为空、是否异常缩短、是否包含不该记录的敏感信息。校验失败时不应该直接覆盖旧 memory。

  - **失败时要保守回退。**
    如果输出不合法，系统应该返回旧 memory，或者只更新合法字段，必要时用“修复格式”的 prompt 重试一次。长期记忆的错误会跨会话持续影响模型，所以宁可不更新，也不要用坏输出覆盖旧记忆。

  - **这和事实 / 推断边界是同一类可靠性问题。**
    prompt gatekeeper 能表达规则，但不能单独保证规则一定被遵守。真正可靠的 memory system，需要在 prompt 之外再加校验、来源、置信度、回退和用户纠错机制。

  所以这点确实和后面“事实和推断边界怎么守”是同一组问题：不能只相信 LLM 的自觉，必须在工程层增加可验证的约束。

### Q17. [重点] 记忆系统真正写进去的“事实”，和模型自己脑补出来的“推断”，边界怎么守？

- **一句总结：**
  memory 和推断的边界要靠“高写入门槛”来守：优先写入可归因的稳定事实，对模型推断保持保守，不要把本轮的合理猜测升级成跨会话的长期背景。

- **详细回答：**
  这条边界的核心原则是：memory 应该优先沉淀“可归因的稳定事实”，而不是沉淀“模型根据上下文推出来的猜测”。因为一旦把推断写进长期记忆，它就会从“本轮可能的判断”升级成“后续每轮都会被重新喂给模型的背景事实”。这比一次性 hallucination 更危险。

  可以分几层看。

  - **先区分“事实”和“推断”。**
    事实通常有比较明确的来源，比如用户明确说过、工具结果明确返回了、文件内容明确写着、项目配置里明确存在。这类信息更适合进 memory。推断则更像“用户可能更喜欢 X”“这个项目大概率是 Y 架构”“看起来之后应该会用 Z”。这些都可能是合理判断，但不应该轻易升级成长期记忆。

  - **memory 写入门槛要比当前回答门槛更高。**
    前台模型在回答时可以做一些合理推断，因为那只是当前轮次输出；但写进长期记忆意味着它会反复影响未来。所以系统应该默认：回答里可以有限推断，memory 里尽量只写高置信事实。

  - **来源要尽量可归因。**
    更稳的 memory system 通常会关心这条记忆来自哪里，比如 user statement、tool result、file content、system inferred。当前 `ch06` 还没有这一层，但你脑子里要先有这个标准：没有来源标记的记忆，可信度天然更低。

  - **把“偏好”和“猜测”区分开。**
    例如“我习惯使用 vim”是用户明确声明，适合进 Global Memory；“用户之前几次都用了 vim，所以可能偏好 vim”是一种模式推断，不能和明确声明同等对待。后者不是不能记，但更适合标成“弱偏好”或带置信度，而不是直接写成硬事实。

  - **对容易过时或可逆的信息更保守。**
    有些信息即使当前像事实，也可能很快变化，比如编辑器偏好、当前分支状态、临时工作目标、近期技术选型。这类信息就算写进 memory，也应该有更高门槛，或者带时间语义，而不是无条件固化。

  - **工业系统里通常会加三层保护。**
    当前 `ch06` 还没有，但从设计上你应该知道后面会往这几个方向走：来源保护，只允许 user/tool/file-derived 信息进入某些 memory 类别；置信度保护，推断型信息必须带 confidence，低置信度不注入主 prompt；纠错保护，用户明确纠正时，能覆盖旧记忆并保留版本痕迹。

  - **这也是为什么记忆更新不能完全信任 LLM 的“整理能力”。**
    `LLMMemoryUpdater` 现在虽然很好用，但它本质上还是一个生成模型。它不仅会抽取事实，也会倾向于“把上下文整理成看起来合理的故事”。对回答来说这可能问题不大；对长期记忆来说，这恰恰是最大风险之一。

  所以更准确地说，边界怎么守，不是靠一句 prompt 就能完全解决，而是要建立一个原则：长期记忆写入时，默认只信明确来源的稳定事实；推断可以辅助当前回答，但不应轻易固化成 memory。

### Q18. 用户明确纠正记忆时，系统应该怎么处理？

- **一句总结：**
  用户明确纠正记忆时，应把它当成最高优先级更新：覆盖或废弃旧记忆，而不是追加并列事实；当前 `ch06` 只能靠 LLM 重写 Markdown 来隐式处理，工业系统通常需要来源、版本和状态字段来显式治理。

- **详细回答：**
  用户明确纠正记忆时，系统应该把它当成高优先级的记忆更新事件，而不是普通对话内容。核心原则是：用户明确纠正 > 用户曾经明确说过 > 模型从行为中推断出来。

  可以分几层看。

  - **先识别这是“纠正”，不是新事实并列。**
    比如用户说“我现在不用 vim 了，我改用 VSCode”。这不是新增一条“用户也用 VSCode”，而是对旧记忆“用户使用 vim”的覆盖。系统需要识别它是在修正已有记忆。

  - **旧记忆应该被覆盖、降权或标记过时。**
    生产系统里一般不会简单把“用户使用 vim”和“用户使用 VSCode”两条都保留成同等事实。这样会让模型以后混乱。更合理的是删除旧记忆，或者标记旧记忆为过时，或者保留版本历史，但注入时只用最新事实。

  - **纠正来源优先级应该最高。**
    用户明确说“不是这样”“我改了”“以后记住 X”，这类输入比模型推断更可靠，也比旧记忆更近。所以它应该覆盖旧的 inferred memory，甚至覆盖旧的 user-stated memory。

  - **需要记录时间或版本语义。**
    对容易变化的信息，比如编辑器偏好、技术选型、项目流程，最好带上“最近更新时间”或版本信息。否则系统后面很难判断哪条更可信。

  - **需要避免只追加不删除。**
    当前 `ch06` 是整份重写 Markdown，理论上后台模型可以把旧内容删掉。但如果 prompt 不够强，它也可能只是追加新说法，导致冲突并存。所以 prompt 里应该明确要求：用户纠正时覆盖旧信息，不要保留已被纠正的过时说法，如果信息冲突，以用户最新明确说明为准。

  - **更工业化的系统会做结构化纠错。**
    比如每条 memory item 都有 `id`、`content`、`source`、`created_at`、`updated_at`、`confidence`、`status: active/deprecated`。用户纠正时，不是让模型自由改一段 Markdown，而是产生明确操作，例如 `deprecate(memory_id)`、`update(memory_id, new_value)` 或 `create(new_memory)`。

  所以当前 `ch06` 的能力边界是：它可以通过 `LLMMemoryUpdater` 的整份重写机制处理纠正，但没有显式版本、来源、状态字段。因此纠错效果主要依赖 prompt 和后台模型是否理解“覆盖旧记忆”。

### Q19. 记忆更新的频率应该怎么设计？为什么现在是每轮都更？

- **一句总结：**
  `ch06` 每轮更新 memory 是为了让你看清楚“对话 -> `CommitTurn` -> `MemoryUpdater` -> 持久化 -> 下轮注入”的完整闭环；真实系统通常会按触发条件、批量、异步、重要性判断来更新，而不是每轮无脑更新。

- **详细回答：**
  是的，每轮都判断并更新长期记忆，开销会偏大，而且不只是钱的问题。当前 `ch06` 这样做，主要是教学实现：链路最清楚、行为最容易观察，但它不是工业系统的最优设计。

  现在 `ch06` 的逻辑大概是：

```text
一轮对话结束
-> CommitTurn()
-> 把本轮新消息正式写入 context
-> 调用 memory.Update(newMessages)
-> 后台模型判断并生成新的 Global / Workspace Memory
-> 写入存储
-> 下一轮 BuildSystemPrompt() 时注入最新 memory
```

  它选择“每轮都更”，有几个教学上的好处。

  - **链路简单。**
    你不用再理解复杂触发器，只要一轮结束，就一定会尝试更新 memory。

  - **方便观察。**
    你每说一句可能影响长期记忆的话，都能看到 `记忆更新: 运行中 / 已完成`，这对学习 memory 闭环很直观。

  - **避免漏掉信息。**
    教学版系统没有复杂的 memory gate，也没有事件分类器，所以最保守的方式就是每轮都交给 `MemoryUpdater` 判断。

  但工业系统一般不会这么做，因为代价比较明显。

  - **模型调用成本。**
    每次 `CommitTurn()` 后都会调用后台模型做 `MemoryUpdater.Update(...)`，这意味着每轮对话至少多一次 LLM 调用。长任务里，这个成本会很明显。

  - **延迟成本。**
    当前实现里 memory update 是在 `CommitTurn()` 里同步执行的。也就是说，它会影响这一轮真正结束的时间，TUI 里会看到 `记忆更新: (运行中...)`。

  - **质量成本。**
    每轮都更新，会让很多低价值、短期、噪声信息也有机会进入 memory。更新频率越高，越容易出现临时信息被长期化、推断被写成事实、旧记忆被无意义改写、记忆内容慢慢漂移。

  - **写入放大。**
    当前是整份重写 memory。即使只改一点点，也会重新生成和写入整份 `Global / Workspace Memory`。如果 memory 变大，这个开销会继续上升。

  更合理的频率设计通常是分层的。

  - **显式触发。**
    用户说“记住这个”“以后都按这个来”“这个项目使用 xxx”，这类语句直接触发 memory update。

  - **重要性触发。**
    先用轻量规则或小模型判断本轮是否包含长期价值信息，只有通过 gate 才进入真正的 memory updater。

  - **批量触发。**
    多轮对话积累到一定数量、一定 token 数、任务结束、用户退出会话时，再统一更新一次。

  - **事件触发。**
    当检测到用户偏好、项目事实、纠正旧记忆、长期目标、稳定约定时更新；普通解释、临时推理、一次性 debug 不更新。

  - **分层频率。**
    `Global Memory` 应该更谨慎、更低频，因为它跨项目影响大；`Workspace Memory` 可以稍微高频，因为它只影响当前项目；如果未来有 `Session Memory`，它可以最高频，因为它生命周期短、污染风险低。

  一个更成熟的设计可能是：

```text
每轮 CommitTurn
-> 先进入本轮上下文
-> 轻量 memory gate 判断是否值得记忆
-> 如果不值得，跳过
-> 如果值得，放入后台更新队列
-> 批量或异步调用 MemoryUpdater
-> 写入结构化 memory 或 markdown memory
-> 下轮请求动态注入最新 memory
```

  这里的核心不是“多久更新一次”，而是“什么信息值得更新到哪一层”。频率设计本质上是成本、及时性、准确性、污染风险之间的工程权衡。

  所以更准确地说，`ch06` 每轮更新是为了教学闭环清楚，而生产系统通常会把 memory update 设计成“有触发条件、有预筛、有批处理、有异步隔离”的后台整理链路。

### Q20. 如果把 `ch06` 做成工业产品，最先该补的 3 个能力是什么？

- **一句总结：**
  如果 `ch06` 要从教学版 memory system 变成工业产品，关键不是先追求“记住更多”，而是先补上 memory gate、结构化 memory store、retrieval-based injection，让记忆系统变得可控、可解释、可纠错。

- **详细回答：**
  如果把 `ch06` 推向工业产品，我会优先补三个能力：memory gate、结构化 memory store、retrieval-based injection。它们分别解决“该不该写”“怎么可靠地存”“每轮该拿哪些出来用”。

  - **Memory Gate：先决定“该不该写”。**
    当前 `ch06` 的链路是：

```text
CommitTurn()
-> memory.Update(draft.NewMessages)
-> LLMMemoryUpdater
-> 重写 Global / Workspace Memory
```

    也就是说，每轮结束后都会把本轮新增消息交给后台模型。后台模型既负责判断“有没有值得记忆的东西”，又负责生成新的 memory。教学上这样很清楚，但工业系统里风险太大，因为 updater 同时承担了两个角色：判断是否值得记忆，以及真正改写长期记忆。

    这两个角色最好拆开。`Memory Gate` 就是 updater 前面的第一道门。它要判断这轮有没有长期价值，这轮信息属于 `Global`、`Workspace` 还是 `Session`，这轮信息是用户明确表达还是模型推断，这轮有没有敏感信息，这轮是不是在纠正旧记忆，以及这轮只是临时任务状态，还是长期偏好或事实。

    一个 gate 的输出可以类似：

```json
{
  "should_update": true,
  "target_scope": "workspace",
  "memory_type": "project_fact",
  "confidence": 0.92,
  "reason": "用户明确说明当前项目使用 Go 1.25+",
  "risk": "low"
}
```

    这样真正的 `MemoryUpdater` 就不用每次都在大段上下文里自己猜“该不该记”。它只处理已经通过 gate 的候选信息。这个能力最重要，是因为长期记忆的最大风险不是漏记，而是误记。漏记最多是下次不知道；误记会在之后很多轮里稳定影响模型行为。尤其当前 memory 会进 system prompt，一旦脏记忆进入，就会被高优先级地反复注入。所以第一优先级应该是控制入口。

  - **结构化 Memory Store：再解决“怎么可靠地存”。**
    当前 `ch06` 存的是 Markdown，更新方式是“旧 memory + 新消息 -> 生成整份新 memory”。优点是简单、可读、适合教学。缺点是工业上很快不够用。

    比如用户说“我之前不用 vim 了，现在改用 VSCode”。Markdown 整份重写时，后台模型可能会正确覆盖旧记忆，也可能变成两条并存的冲突记忆：用户习惯使用 vim，用户现在使用 VSCode。系统没有明确知道哪条是旧的、哪条是新的、哪条已经被废弃。

    结构化 memory store 会把每条记忆变成一个 item：

```json
{
  "id": "mem_123",
  "scope": "global",
  "type": "user_preference",
  "content": "用户偏好使用 VSCode 作为编辑器",
  "source": "user_explicit",
  "created_at": "2026-04-24T10:00:00Z",
  "updated_at": "2026-04-24T12:30:00Z",
  "confidence": 1.0,
  "status": "active",
  "replaces": ["mem_001"]
}
```

    这样系统就可以更新某一条 memory、废弃某一条 memory、保留版本历史、追踪来源、判断可信度、按 scope 检索、按 type 注入、按时间衰减、审计某条记忆为什么存在，以及删除敏感记忆。

    结构化存储还可以把 memory 分成不同类型，比如 `user_preference`、`project_fact`、`workflow_rule`、`task_state`、`correction`、`sensitive_candidate`。不同类型应该有不同策略：`user_preference` 要谨慎写入并尊重用户纠正；`project_fact` 最好有文件或 tool 证据；`workflow_rule` 不能轻易进入高优先级 prompt；`task_state` 更适合 `Session Memory`，不适合长期保存；`sensitive_candidate` 默认不写或需要用户确认。

    这就是为什么结构化 store 是第二优先级。没有它，后面很难做纠错、冲突管理、审计和安全治理。

  - **Retrieval-Based Injection：最后解决“每轮该用哪些记忆”。**
    当前 `ch06` 的注入方式是：

```text
memory.String()
-> 把 Global / Workspace 全量拼进 system prompt
```

    教学上很直观，因为模型每轮一定看见记忆。但工业系统里，全量注入会带来 token 成本越来越高、无关 memory 干扰当前任务、过时 memory 继续影响模型、敏感信息暴露面变大、system prompt 被长期记忆挤占、模型可能过度服从旧记忆等问题。

    更合理的方式是按需检索：

```text
用户当前 query
+ 当前 workspace
+ 当前任务类型
+ 最近对话状态
-> 检索相关 memory items
-> 过滤低置信/过期/无关项
-> 只注入少量最相关 memory
```

    例如用户问“这个项目怎么跑测试？”，系统应该优先注入当前项目相关的 `Workspace Memory`，比如“本项目使用 `go test -v ./...`”或“`ch06` 当前测试可能受本地 Go 版本影响”。它不应该同时注入用户喜欢 vim、用户喜欢学习笔记用 Q&A、之前 `ch03` 讨论过 `reasoning_content`、某个旧项目使用 React 之类的无关信息。

    按需注入还要考虑优先级。更合理的顺序是：当前用户明确指令 > 当前工具或文件事实 > 高置信 `Workspace Memory` > 高置信 `Global Memory` > 低置信推断。并且 system prompt 里最好写清楚：memory 是历史背景，不是绝对真理；如果 memory 与当前用户指令、工具结果、文件事实冲突，应以当前事实为准。

    这能降低 memory 反向污染主模型行为的风险。

  这三个能力刚好覆盖 memory 系统的三段关键路径：写入前的 `Memory Gate`，存储中的 `Structured Memory Store`，读取时的 `Retrieval-Based Injection`。也就是先决定该不该写，再决定怎么可靠地存，最后决定该怎么拿出来用。

  如果没有 gate，系统会写入脏数据。如果没有结构化 store，系统写进去以后不可解释、不可纠错。如果没有按需注入，系统会把所有记忆都塞进主模型，造成上下文污染。

  所以它们不是锦上添花，而是长期记忆从 demo 走向产品的最小治理闭环。
