# Ch05 学习笔记

## 本章需要学习的内容

- **本章主线：**
  这一章真正新增的不是某一个新 tool，而是 Agent 开始具备“在有限上下文窗口内持续运行”的能力。主角从 `agent` 进一步转移到了 `context.Engine`，核心问题变成了：消息什么时候保留、什么时候压缩、什么时候卸载、什么时候删除。

- **核心抽象：**
  需要重点理解 `Engine`、`Policy`、`Summarizer`、`Storage` 这几个抽象之间的职责边界。`Engine` 负责统一管理上下文状态和策略执行，`Policy` 负责定义具体压缩策略，`Summarizer` 负责把摘要能力从策略中解耦出来，`Storage` 负责承接被卸载的长内容。

- **三种上下文策略：**
  需要分别理解 `truncate`、`offload`、`summarize` 各自解决什么问题，为什么它们不能互相完全替代，以及它们组合起来时为什么会形成一套工程化的上下文管理机制。

- **状态边界：**
  这一章有一个很关键的实现意识，就是把“本轮草稿消息”和“正式上下文状态”分开。`StartTurn`、`BuildRequestMessages`、`CommitTurn`、`AbortTurn` 这套接口不是形式设计，而是在确保上下文变更只在合适时机落盘到引擎内部。

- **策略协同：**
  本章不只是三个策略各自能跑，而是三者如何按顺序协同。你需要理解为什么 policy 设计成链式执行，为什么每个策略都通过 `ShouldApply` 决定是否触发，以及阈值、批大小、保留条数这些参数为什么会直接影响 Agent 的运行质量。

  你要能说明为什么 Agent 不能只靠模型的大上下文窗口硬撑，以及为什么上下文工程同时关乎成本、稳定性、响应质量和长任务可持续性。

  你要能说明 `context.Engine` 为什么是这章真正的核心，以及它是怎么把消息状态管理、请求构建、turn 提交和 policy 执行统一起来的。

- **三种策略的分工：**
  你要能明确区分：`truncate` 解决“历史太长时怎么删”，`offload` 解决“长原文怎么搬出上下文但还能回读”，`summarize` 解决“历史怎么压缩成保留关键事实的摘要”。

  你要能解释 policy 链为什么有顺序，为什么不同阈值和参数会导致完全不同的运行行为，以及为什么这本质上是一个工程调参问题，不只是算法选择问题。

  你要能说明 `Summarizer` 接口为什么要单独存在，它如何把“什么时候摘要”和“怎么摘要”分开。

  你要能解释为什么 `draft` 和正式 `messages` 必须分离，以及这和流式中断、tool loop、多策略执行之间有什么关系。

  你要能判断这章虽然已经实现了基础上下文治理，但离更完整的 memory、分层存储、长期记忆检索、策略评估和生产级调参体系还有距离。

  Anthropic 这组材料主要分成两篇。`Context windows` 解释了上下文窗口本质上是模型的工作记忆，不是越大越好；随着上下文增长，准确性和检索能力会出现退化，也就是 `context rot`。它还强调 extended thinking 和 tool use 会改变有效上下文的计算方式，尤其是前面轮次的 thinking blocks 会被 API 自动从后续上下文计算里剥离。`Managing context on the Claude Developer Platform` 则更偏工程方法，重点讲长任务里的 agent 为什么会被工具结果和历史状态拖垮，以及 Anthropic 如何把 context management 拆成主上下文内的清理和上下文外的 memory 保存两类能力。

- **和 `ch05` 的对应关系：**

  - 第一，上下文窗口是预算池，不是仓库，重点不是能装多少，而是该让什么继续留在里面。

  - 第四，context management 至少有两层：主上下文内的清理 / 压缩，以及上下文外的记忆 / 外置存储。
  - 第五，这本质上是工程调参问题，不只是摘要算法问题，什么时候清、清什么、保留多少、哪些外置、哪些跨会话保留，都会直接影响 agent 质量。

- **把代码行为映射到真实 Agent 系统：**
  不要只把它理解成教学 demo。你需要不断追问：这套机制在真实 Agent 系统里分别对应什么能力，解决什么问题，还有哪些缺口。

- **读 `policy_test.go` 时要重点看边界，不只看断言：**
  这份测试文件最值得学的不是“测没测通过”，而是它在定义作者允许什么、不允许什么。你要重点关注 6 个点：第一，`truncate` 不是随便删，而是尽量卡在 `user` 边界，说明它是在保护对话语义链；第二，`truncate` 也有保护区，落在 `keepRecent` 范围内时宁可不删；第三，`summarize` 的核心不是一次性生成摘要，而是分批处理并带着 running summary 递进；第四，摘要最终被刻意实现成一条 `user` 消息，这说明它不是偶然实现，而是明确的上下文语义选择；第五，摘要失败时系统要保守回退，宁可保留原文，也不要用坏摘要替换历史；第六，`offload` 只处理长 `tool` 消息，而且 storage 失败时必须保留原文，不能静默损坏内容。读这些测试时，最值得追问的是：这条测试在保护什么边界，如果没有这条边界，真实 Agent 会怎么坏掉。

## 本章应掌握的核心知识点

- **本章新增的是“上下文治理能力”，不是“再加一个功能模块”。**
  `ch05` 真正做的事情，是让 Agent 开始能在有限上下文窗口中持续工作，而不是依赖模型窗口无限增长。你要把它理解成 Agent 运行时能力的一次升级。

- **`context.Engine` 是本章真正的核心对象。**
  这章的主角已经不只是 `Agent`，而是 `Engine`。它把系统提示、历史消息、token 计数、turn 提交和 policy 执行整合在一起，成为上下文状态的统一管理器。

- **三种 policy 不是并列 feature，而是三类不同治理动作。**
  `truncate` 是删除历史，`offload` 是外置长内容并保留回读入口，`summarize` 是压缩历史语义。它们看起来都在“减少上下文”，但减少的方式、保留的信息类型和适用场景都不同。

- **这章真正重要的是“策略链”，不是某个单一策略。**
  `Policy` 接口让不同上下文策略可以按顺序协同执行。你要理解的重点是：上下文治理在工程上往往不是单一算法，而是多个策略叠加后的整体行为。

- **摘要能力被单独抽象出来，说明“什么时候摘要”和“怎么摘要”是两层问题。**
  `SummaryPolicy` 只负责判断是否摘要、摘要哪些消息；真正的摘要生成由 `Summarizer` 完成。这种拆层是为了替换实现、便于测试，也说明摘要本身是一个独立能力。

- **这章已经开始引入“短期上下文”和“外置内容”分层。**
  `offload + load_storage` 的组合，意味着不再把所有有用信息都硬塞进模型上下文，而是允许部分内容外置存储，再在需要时按需加载。这是后续 memory / storage 体系的前奏。

- **上下文状态边界是这章很关键的实现意识。**
  `StartTurn`、`BuildRequestMessages`、`CommitTurn`、`AbortTurn` 这套接口说明：本轮输入、流式输出、tool loop 和正式上下文提交是分阶段的。只有完整成功的一轮，才应该真正进入正式上下文状态。

- **这章已经有工程味，但还不是完整的长期记忆系统。**
  它解决的是“有限窗口内如何活下去”，还没有真正解决“长期记忆如何组织、如何检索、如何评估价值”。所以你要知道：`ch05` 是上下文工程起点，不是终点。

## 三种策略速览

- **`truncate`：**
  直接删除更早历史，优先保留最近对话连续性。它保的是“最近几轮还看得见”，牺牲的是更早历史的完整性，适合当前任务最重要、旧历史可以放弃的场景。

- **`offload`：**
  把长原文搬到外部存储，在上下文里只保留预览和恢复入口。它保的是“原文仍可恢复”，牺牲的是“当前上下文里不能直接看到全文”，适合长 `tool` 输出这类原始材料。

- **`summarize`：**
  把多条历史压缩成更短的摘要消息。它保的是“任务主线和关键事实”，牺牲的是“原始表达和细节证据”，适合历史不能直接丢、但也没必要继续保留原文的场景。

- **三者的根本区别：**
  `truncate` 是删，`offload` 是外置，`summarize` 是压缩。它们都在减少上下文，但减少的是不同类型的信息，所以不能互相简单替代。

## Q&A

### Q1. [重点] 为什么 `ch05` 要单独引入一个 `context.Engine`，而不是继续把消息列表直接挂在 `Agent` 里管理？

- **一句总结：**
  `ch05` 单独引入 `context.Engine`，是因为消息列表在这一章已经不再只是历史记录，而是需要被统一治理的上下文状态；把它独立出来，才能把上下文管理和 Agent 执行逻辑真正分层。

- **详细回答：**
  因为到了 `ch05`，消息列表已经不再只是“对话历史”，而变成了一份需要被计算、裁剪、替换、外置和重建的运行时状态。这个职责继续塞在 `Agent` 里，会让 `Agent` 同时承担太多不同层次的工作。

  可以从几个角度理解。

  - **前几章的消息管理还是“被动累加”，这一章变成了“主动治理”。**
    在前面的实现里，消息更多只是随着对话和 tool loop 持续 append。到了 `ch05`，消息不再只是简单累积，而是会被 policy 改写：可能被截断，可能被摘要替换，也可能被外置存储后改写成预览消息。一旦消息链会被系统主动重写，它就已经不是普通字段了，而更像一个专门的状态对象。

  - **`Agent` 和 `context.Engine` 解决的是两类问题。**
    `Agent` 负责调模型、跑 tool loop、处理 MCP / native tools、驱动一轮任务执行；`context.Engine` 负责管理上下文状态、统计 token、构造请求消息、执行策略链、决定一轮结束后哪些消息正式进入上下文。这说明两者的抽象边界已经明显不同了。继续把消息列表挂在 `Agent` 上，会把“任务执行逻辑”和“上下文治理逻辑”缠在一起。

  - **上下文工程需要统一入口和统一状态机。**
    `ch05` 不是只做一个“摘要函数”或者“截断函数”，而是引入了一套完整流程：`StartTurn`、`BuildRequestMessages`、`CommitTurn`、`AbortTurn`、`applyPolicies`。这已经是一个完整的小状态机了。一旦你需要这种“回合开始、回合提交、失败回滚、策略后处理”的生命周期管理，就更适合单独抽一个 `Engine`，而不是在 `Agent.RunStreaming()` 里零散处理。

  - **上下文治理需要独立演进。**
    一旦单独引入 `context.Engine`，后面就更容易继续扩展：增加新的 policy、替换摘要器、引入 memory、接入更复杂的 storage、做不同模型的 token budget 管理。如果这些都耦合在 `Agent` 里，后面每加一类能力，`Agent` 都会继续膨胀。

  - **这是一种分层信号：上下文开始被视为一等公民。**
    前几章里，上下文更多是 Agent 的附属状态；这一章开始，上下文被单独提升成一个独立子系统。这很重要，因为真实 Agent 系统里，“上下文怎么组织”本身就是核心能力，不能一直只是 `[]messages`。

  所以更准确地说，`ch05` 引入 `context.Engine`，不是为了代码好看，而是因为上下文已经从“Agent 的一个字段”升级成了“需要独立治理、独立演进、独立建模的运行时子系统”。

### Q2. [重点] `StartTurn / BuildRequestMessages / CommitTurn / AbortTurn` 这套 turn 生命周期，到底在保护什么状态边界？

- **一句总结：**
  这套 turn 生命周期保护的是“临时执行状态”和“正式上下文状态”的边界，确保只有完整成功的一轮消息才会进入上下文，并成为后续 policy 和模型请求的正式输入。

- **详细回答：**
  它在保护的核心边界是：“本轮临时生成的消息”和“已经被正式接纳进上下文的消息”必须分开。这是 `ch05` 很关键的状态设计，不然上下文工程会很容易把半成品、失败结果或脏状态写进正式历史。

  可以分几层看。

  - **`StartTurn` 代表“开始构造一轮草稿”。**
    它并不直接修改 `Engine` 内部消息，而是先创建一个 `TurnDraft`，把本轮新增消息放进草稿区。这样用户输入虽然已经进入本轮执行链路，但还没有被正式写入上下文。

  - **`BuildRequestMessages` 代表“基于当前稳定上下文构造这次请求”。**
    这里拼出来的是 system prompt 和已经正式存在于 `Engine` 里的历史消息。然后 `Agent` 再把当前 `draft.NewMessages` 追加进去，作为本轮请求使用。也就是说，发给模型的请求可以包含“历史 + 本轮草稿”，但 `Engine` 自己仍然只持有稳定历史。

  - **`CommitTurn` 代表“这一轮成功完成，可以正式入账”。**
    只有在整轮执行成功之后，草稿消息才会被 append 进 `Engine.messages`，然后再触发 token 重算和 policy 链。这说明 policy 处理的对象不是半成品，而是“已经完成的一轮新消息”。

  - **`AbortTurn` 代表“这一轮不成立，不应该污染上下文”。**
    当前实现里它是 no-op，是因为草稿本来就还没写进 `Engine`。这反而正说明设计是对的：因为正式状态和临时状态已经分开，所以 abort 时根本不需要再做复杂回滚。

  这套生命周期保护的状态边界，本质上有三个层面。

  - **保护正式上下文不被半成品污染。**
    如果模型流到一半断了、tool call 中途失败了、或者本轮被用户取消了，就不应该把这轮不完整消息直接算作“历史事实”。

  - **保护 policy 只处理稳定输入。**
    `truncate`、`offload`、`summarize` 这些策略都应该在“一轮完成后”再作用于上下文，而不是边流式边改历史，否则状态会非常难推理。

  - **保护执行层和上下文层的职责分离。**
    `Agent` 负责跑这一轮；`Engine` 负责决定这一轮结束后，哪些内容正式进入上下文，以及进入后是否要被进一步治理。

  所以你可以把这套生命周期理解成：`StartTurn` 是开始一张临时单据，`BuildRequestMessages` 是拿稳定账本 + 当前单据去执行，`CommitTurn` 是执行成功后正式入账，`AbortTurn` 是执行失败后单据作废。

- **流程图：**

```text
[稳定上下文]：Engine.messages
        |
        v
[StartTurn]：创建 TurnDraft
        |
        v
[BuildRequestMessages]：取稳定历史 + system prompt
        |
        v
[Agent]：追加 draft.NewMessages，发起本轮请求
        |
        v
[判断]：本轮是否完整成功？
  |                           |
  | 是                        | 否
  v                           v
[CommitTurn]：把 draft 写入   [AbortTurn]：丢弃草稿，
Engine.messages               不污染正式上下文
  |
  v
[recountTokens]：重算 token
  |
  v
[applyPolicies]：执行 truncate / offload / summarize
  |
  v
[新的稳定上下文]
```

### Q3. `AbortTurn` 什么都没做？

- **一句总结：**
  `AbortTurn` 现在是 no-op，不是因为不重要，而是因为 `TurnDraft` 机制已经保证了失败的一轮从未污染 `Engine.messages`，因此无需回滚。

- **详细回答：**
  对，当前实现里 `AbortTurn` 什么都没做，而且这是刻意设计，不是漏写。

  关键点在于：`StartTurn` 只创建了一个 `TurnDraft`，本轮新增消息先都放在 `draft.NewMessages`，在 `CommitTurn` 之前，这些草稿消息并没有写进 `Engine.messages`。所以当一轮失败、取消或中断时，`AbortTurn` 不需要回滚正式上下文，因为正式上下文本来就没被改过。

  更准确地说：如果状态是“先写正式历史，再失败时回滚”，那 `AbortTurn` 就会很复杂；现在的状态是“先写草稿，成功后再提交”，那 `AbortTurn` 自然可以是 no-op。

  所以这里的重点不是 `AbortTurn` 做了什么，而是它之所以可以什么都不做，是因为前面的状态边界设计已经把脏状态隔离在正式上下文之外了。

### Q4. `CommitTurn` 为什么是在整轮 tool loop 结束后才触发 policy，而不是中途边生成边治理？

- **一句总结：**
  `CommitTurn` 放在整轮 tool loop 结束后才触发 policy，是因为上下文治理要处理的是一轮完整结果，而不是执行中的半成品；这样才能保证语义闭合、状态稳定和回滚简单。

- **详细回答：**
  因为 `policy` 治理的对象应该是一轮已经稳定完成的上下文结果，而不是执行到一半的临时状态。

  如果中途边生成边治理，会马上出现几类问题。

  - **tool loop 还没结束，语义链还没闭合。**
    一轮里可能是：assistant 先决定调用 tool，tool 返回结果，assistant 再基于结果继续回答。如果你在中途就开始 `truncate`、`offload` 或 `summarize`，处理到的其实是半截上下文。这样很容易把一轮完整因果链拆开。

  - **临时状态会污染正式上下文。**
    `ch05` 现在刻意把本轮草稿消息和正式上下文消息分开管理。如果边生成边治理，就等于把还没确认成功的内容提前写进正式状态，然后再去压缩、替换、外置。这会让失败回滚变复杂很多。

  - **policy 需要稳定输入，不能对流式增量反复改写。**
    `offload`、`summarize`、`truncate` 都是假设自己面对的是一份完整消息列表。如果流式过程中每来一点内容就触发一次，token 计数会抖动，摘要输入会不断变化，被 offload 的内容可能还没完整，截断边界也可能后面又变了，这样策略行为会非常不稳定。

  - **工程复杂度会大很多。**
    一旦中途治理，你就要处理：正在生成的 assistant 消息能不能被摘要，正在返回的 tool result 能不能被 offload，policy 改写后当前这轮请求上下文怎么算，以及用户中途取消时如何回滚已经治理过的状态。这会把 `context.Engine` 从“回合后治理”升级成“执行中动态状态机”，复杂度会上一个层级。

  所以现在的设计其实很明确：一轮执行阶段只负责把这轮完整跑完；一轮提交阶段把完整结果写入上下文；提交后治理阶段再统一执行 `policy`。这保证了 policy 面对的是“完整、稳定、可推理”的输入。

### Q5. [重点] `truncate / offload / summarize` 这三种 policy 看起来都在“减少上下文”，但它们本质上分别在保留什么、牺牲什么？

- **一句总结：**
  `truncate` 保最近、丢远史；`offload` 保原文可恢复、牺牲即时可见；`summarize` 保任务语义、牺牲原始细节。三者都在减上下文，但减的是不同类型的信息。

- **详细回答：**
  这三个策略表面上都在“让上下文变短”，但本质上它们是在用三种不同方式处理历史信息价值。真正的区别不在“减了多少”，而在：想保住什么，愿意牺牲什么，恢复成本是多少，对模型理解连续性的影响有多大。

  可以分别看。

  - **`truncate`：优先保留最近对话连续性，牺牲远期历史。**
    `truncate` 的思路最直接，就是把早期消息删掉，只留下最近一段。它真正保住的是最近几轮的上下文连续性、当前任务附近的交互语境，以及最低的实现复杂度和最低的恢复成本。它真正牺牲的是远期历史细节、之前的用户目标、工具结果、决策过程，以及长任务的全局一致性。所以 `truncate` 更像一种“把注意力集中在眼前”的策略。它简单、稳定，但对长期任务最不友好。

  - **`offload`：优先保留“可恢复的原始信息”，牺牲即时可见性。**
    `offload` 不是真的把信息删掉，而是把长内容移出主上下文，只在上下文里留预览、存储 key 和一个显式的恢复入口。它真正保住的是原始信息仍然存在，后续需要时可以按需读回，以及长工具输出不会一直占据上下文窗口。它真正牺牲的是模型不能在当前上下文中直接看到全文；如果后面要用到完整信息，就必须额外调用 `load_storage`；推理链也会因此多一步“发现信息已外置并主动恢复”。所以 `offload` 的特点是：信息完整性保住了，但即时可用性下降了。

  - **`summarize`：优先保留语义和事实，牺牲原始表达细节。**
    `summarize` 不是删，也不是搬走，而是把多条历史压缩成一条更短的语义表示。它真正保住的是任务主线、关键事实、重要工具调用和结果，以及对长期任务的整体理解。它真正牺牲的是原始措辞、完整中间过程、细粒度证据，以及摘要过程中可能丢失的小但关键的上下文信号。所以 `summarize` 的特点是：它保的是“意思”，不是“原文”。

  如果把三者压成一张对照图，可以这样理解：`truncate` 保最近交互连续性，但更早历史基本不可恢复；`offload` 保原始全文可恢复性，但丢掉当前上下文中的即时可见性；`summarize` 保核心语义和任务主线，但通常不能精确恢复原文。

  所以为什么这三种策略不能互相替代？因为它们其实在解决三种不同问题：如果问题是“最近对话最重要，旧内容可以丢”，那就偏 `truncate`；如果问题是“原文很长但后面可能还要用”，那就偏 `offload`；如果问题是“历史不能直接丢，但也没必要保全文”，那就偏 `summarize`。这也是 `ch05` 设计成 policy 链而不是单一策略的原因。因为真实上下文治理里，信息不是只有“保留/删除”两种命运，而是至少有三种处理方式：删除、外置、压缩。

### Q6. 为什么 `truncate` 要尽量卡在最后一个 `user` 边界，而不是简单按条数直接砍？

- **一句总结：**
  `truncate` 尽量卡在最后一个 `user` 边界，是因为 user 消息通常是一轮意图的起点；从这里开始保留，能最大程度避免把对话因果链从中间砍断。

- **详细回答：**
  因为 `truncate` 删掉的不只是“几条消息”，而是在切一段对话语义链。如果只按条数硬砍，很容易把一段完整交互从中间切断，让模型看到一个残缺上下文。

  `ch05` 里专门去找“可裁剪区里最后一个 user 消息”，本质上是在尽量把截断点放到一个语义上更自然的边界上。

  可以从几个角度理解。

  - **user 消息通常是一轮意图的起点。**
    一段典型交互往往是：user 提问题或提出任务，assistant 回应，tool call / tool result，assistant 总结。所以如果你从一个 user 消息开始保留，后面那一串 assistant、tool、tool result 至少还有“这是谁的问题、为什么要做这些动作”的语义锚点。

  - **如果按条数硬砍，很容易把因果链砍断。**
    比如你可能保留下来了一条 tool result 和一条 assistant 总结，但前面的 user 请求已经被删掉了。这时模型虽然还能看到“发生了什么”，却不一定知道“为什么发生”，上下文可理解性会明显下降。

  - **user 边界是对话里最自然的分段点。**
    截断时你总要在某个地方下刀。相比 assistant 中间回复、tool result 中间节点，user 消息更像一轮任务的起始标记。把截断点放在这里，通常比从别的角色中间切进去更稳。

  - **这是一种低成本的“语义保真”手段。**
    `truncate` 本来就是最粗暴的策略，没有摘要，也没有恢复能力。所以在它内部，作者会尽量做一些便宜但有效的保护动作。“优先卡在最后一个 user 边界”就是这种很典型的工程优化：几乎不增加复杂度，但能显著减少语义断裂。

  - **这也说明 `truncate` 不是纯粹的 token 操作，而是语义感知删减。**
    虽然它仍然很粗糙，但它已经不是“为了省 token 随便删”，而是在尝试保住最基本的对话结构。

  还有一个细节很重要。代码里如果找不到合适的 user 边界，或者边界太靠前，甚至会选择不删。这说明作者宁愿保守一点，也不想把上下文删成一个难以理解的残片。

### Q7. 为什么 `offload` 只处理长 `tool` 消息？它是不是把历史对话存到 storage，再暴露一个 `load_storage` tool 给模型决定是否恢复全文？

- **一句总结：**
  `offload` 先只处理长 `tool` 消息，是因为它们最容易造成上下文膨胀、最适合外置回读；它本质上就是把这类长内容外置到 storage，并通过 `load_storage` 工具把“是否恢复全文”的决定权交给模型。

- **详细回答：**
  因为 `offload` 在这章里的目标，不是“把所有长文本都搬走”，而是优先处理最容易膨胀、但又最适合外置的那类上下文。当前实现里，这类消息就是长 `tool` 输出。

  可以从几个角度看。

  - **长 `tool` 输出通常是上下文膨胀的主要来源。**
    在 Agent 系统里，真正容易把上下文撑爆的，往往不是用户一句话，也不是 assistant 最终回答，而是工具返回的大段原始结果，比如文件全文、命令行长输出、搜索结果列表、API 原始响应。所以 `offload` 先盯 `tool` 消息，是因为这类消息最常见、最重、收益最大。

  - **`tool` 消息天然更适合“外置 + 按需回读”。**
    很多 `tool` 输出本来就是“原始材料”，不是最终要给用户直接看的成品。把它外置后，仍然保留一段预览、一个 `load_storage(key=...)` 的恢复入口。这个语义是比较自然的：模型知道“如果需要全文，可以再去取”。但如果把用户消息或 assistant 回复也这样处理，语义就会变得奇怪，因为那些消息本来就是对话主线的一部分，不只是原始材料。

  - **用户消息和 assistant 消息更像“对话骨架”，不应轻易外置。**
    用户消息里可能包含真实需求、约束、偏好；assistant 消息里可能包含阶段性结论、解释和决策。这些内容如果也被替换成“预览 + 外置 key”，就会直接削弱对话连续性。换句话说：`tool` 消息更像“证据材料”，`user/assistant` 消息更像“任务主线”。`offload` 当前选择只动前者，是在保护后者。

  - **为什么需要 `load_storage`，而不是只留预览就够了。**
    只留预览，只能解决“知道这段内容存在”，不能解决“重新获得这段内容”。如果没有 `load_storage`，那 `offload` 更像“弱删除”：原文虽然物理上还在 storage 里，但模型没有办法主动把它取回来。有了 `load_storage`，`offload` 才真正变成“外置化”：长内容退出主上下文，但仍然保留可恢复性。

  - **这其实是一组配套机制。**
    `offload` 做的是两件事：第一，把长内容从主上下文里移出去；第二，把“恢复这段内容的能力”以 tool 的形式交给模型。也就是说，前者负责搬出去，后者负责在需要时再搬回来。

  - **这是当前实现的保守起点，不代表永远只能这样。**
    这章的设计更像一个工程上可接受的 first step：先把最典型、最重、最适合外置的 `tool` 输出处理掉。后面如果系统更成熟，当然可以进一步演进，比如对某些超长 user 输入做特化处理、对某些 assistant 的长分析结果做结构化外置，或者按消息类型做不同 offload policy。但教学实现先把 `tool` 输出拿下，是最稳的切口。

  所以更准确地说，`offload` 不处理所有长消息，不是因为别的长消息不重要，而是因为长 `tool` 消息既是上下文膨胀的主要来源，又最像“可外置的原始材料”；而用户和 assistant 消息更属于对话主线，轻易外置会直接伤到语义连续性。同时，`load_storage` 也不是可有可无的附加件，而是让 `offload` 从“只留预览”变成“按需恢复全文”的关键恢复通道。

### Q8. `offload` 处理的是 `tool` 消息，那模型怎么知道该加载哪次被 offload 的内容？

- **一句总结：**
  模型之所以知道该加载哪次 offload 的内容，是因为每条被外置的 `tool` 消息在上下文里都会保留预览和对应的 `key`，模型直接根据这条消息里的恢复提示决定是否调用 `load_storage`。

- **详细回答：**
  靠两层线索：消息里的预览内容，以及消息里的 `load_storage(key="...")` 提示。

  当前 `offload` 并不是把 tool 消息彻底藏起来，而是把原消息改写成：前面一小段原文预览、一个明确的 storage key，以及一句提示，告诉模型可以用 `load_storage` 取全文。所以模型在后续上下文里其实还能看到：这是哪条 tool 消息的大致内容，以及如果要恢复，应该用哪个 key。

  也就是说，模型不是“凭空猜哪次 offload 过”，而是从上下文里那条被改写后的 tool 消息直接读到恢复入口。

  例如它看到的是这种形式：

```text
这是一个非常长的工具输出前 100 个字符...
（更多内容已卸载，如需查看全文请使用 load_storage(key="/offload/20260419_123456_3") 工具）
```

  那它后面如果判断这段预览已经够用，就不加载；如果判断预览不够、需要细节，就调用 `load_storage(key="/offload/20260419_123456_3")`。

  所以这里的关键不是“模型记忆哪次 offload”，而是每条被 offload 的消息自己就带着恢复指针。

### Q9. 为什么 `summarize` 最后生成的是一条 `user` 消息，而不是 `system` 或 `assistant` 消息？

- **一句总结：**
  `summarize` 生成一条 `user` 消息，不是因为它真的是用户说的，而是因为摘要既不该提升成 `system` 规则，也不该伪装成 `assistant` 原话；在现有角色里，`user` 是相对中性、风险更低的折中选择。

- **详细回答：**
  因为在当前实现里，这条摘要更像是给后续模型看的历史事实补充，而不是新的系统规则，也不是 assistant 刚刚说过的一句话。三种角色里，`user` 是最“中性且安全”的落点。

  可以分开看。

  - **为什么不是 `system`：**
    `system` 消息的语义太强了。它通常用来定义高优先级行为规则、身份设定、输出约束。如果把摘要放成 `system`，模型更可能把它当成新的指令层，而不是“历史对话被压缩后的记录”。这会混淆两种本来应该分开的东西：系统规则和会话历史摘要。所以从语义边界上说，摘要不应该冒充 `system`。

  - **为什么不是 `assistant`：**
    如果放成 `assistant`，它看起来就像是 assistant 曾经真的说过这段话。但实际上这条摘要并不是某一轮 assistant 的原始输出，而是系统为了上下文治理，把多轮历史重新压缩出来的一段“二次加工产物”。放成 `assistant` 会制造一种错觉：这段摘要是自然发生的会话内容，而不是系统生成的历史压缩结果。

  - **为什么 `user` 在这里更中性：**
    在当前实现里，`user` 并不是说“真的是用户说的”，而是说它比 `system` 弱、比 `assistant` 更不容易伪装成自然对话成品。把摘要作为一条普通消息塞回上下文，`user` 是一个相对保守的选择：不会提升成系统指令，不会假装是 assistant 的原话，但仍然能被模型当作上下文内容读取。

  - **这也说明当前实现是教学化、简化的。**
    更严格地说，这条摘要其实不是特别天然地属于 `user`。它只是当前几种角色里最不容易造成严重语义误导的那个。在更成熟的系统里，你可能会看到更清晰的做法，比如单独的 summary role、metadata 标记的上下文节点，或者 memory / context note 专用结构。但 OpenAI-style chat message 这套接口没有这种原生角色，所以教学实现只能在现有角色里选一个最稳妥的落点。

  - **这也带来一个隐含风险：**
    因为它毕竟不是“真实用户消息”，放成 `user` 只是折中方案。所以你后面如果继续做工业化，通常会进一步考虑给摘要内容加更明确的前缀、做结构化 memory，而不是伪装成普通消息，或者把“摘要事实”和“真实对话”区分开。

### Q10. [重点] 为什么 `summarize` 不直接写在 `SummaryPolicy` 里，而要再抽一个 `Summarizer` 接口？

- **一句总结：**
  `summarize` 不直接写死在 `SummaryPolicy` 里，是因为“何时摘要”属于上下文策略，“怎么摘要”属于摘要实现；抽出 `Summarizer` 能获得替换性、可测试性和后续演进空间。

- **详细回答：**
  因为 `SummaryPolicy` 和 `Summarizer` 其实在解决两层不同的问题：`SummaryPolicy` 决定“什么时候摘要、摘要哪些消息、摘要完怎么替换上下文”，`Summarizer` 决定“具体怎么把这些消息变成摘要文本”。如果把这两层写死在一起，短期省几行代码，后面很快就会失去替换性和测试性。

  可以从几个角度看。

  - **“摘要时机”和“摘要算法”是两类职责。**
    `SummaryPolicy` 关心的是上下文治理逻辑，比如什么时候触发、保留最近多少条、一批摘要多少消息、摘要后如何替换历史消息。这些都属于“上下文管理策略”。而 `Summarizer` 关心的是用哪个模型、prompt 怎么写、输入上限是多少、怎么把 running summary 和新消息合并。这些属于“摘要实现”。这两类变化频率和关注点都不同，应该拆开。

  - **后面很可能不只一种摘要器。**
    当前实现是 `LLMSummarizer`，但后面完全可能出现更便宜的小模型摘要器、本地模型摘要器、规则型摘要器，或者针对代码 / 客服 / 检索任务的专用摘要器。如果摘要逻辑写死在 `SummaryPolicy` 里，每换一种实现都要改 policy 本身。抽成接口后，policy 不变，只换 summarizer。

  - **更容易测试。**
    你在 `policy_test.go` 里已经能看到这个设计的直接收益：`fakeSummarizer` 可以很容易注入进来，单测就能只验证 batching 对不对、running summary 是否正确传递、空摘要时是否回退原消息。如果 `SummaryPolicy` 自己直接调 LLM，测试会又慢又重，还很难稳定。

  - **让 `SummaryPolicy` 保持“策略对象”身份。**
    如果 policy 里直接持有完整 LLM 调用、prompt 构造、模型配置、输入截断逻辑，那它就不再只是 policy 了，而会变成“策略 + 模型客户端 + prompt 工程”的混合体。职责会发散得很快。

  - **这是为后面 memory / storage 演进留接口。**
    未来如果摘要不仅仅是“压缩聊天记录”，还可能是生成长期记忆条目、生成结构化摘要、生成可检索摘要、生成不同粒度的摘要版本。那时候 `SummaryPolicy` 仍然只是决定“何时触发摘要治理”，而真正的摘要产物形态可以交给不同 `Summarizer` 实现。

  所以更准确地说，抽 `Summarizer` 不是为了“面向接口而接口”，而是因为上下文治理中的“策略决策层”和“摘要生成层”本来就应该分开。

### Q11. [重点] 为什么 `Policy` 要设计成接口 + 链式执行，而不是在 `Engine` 里写死一套固定的上下文压缩流程？

- **一句总结：**
  `Policy` 用接口 + 链式执行，是因为上下文治理天然是多策略、可组合、可调顺序、可扩展的问题；`Engine` 负责统一调度，具体治理动作交给各个 policy 才不会耦合失控。

- **详细回答：**
  因为这章要解决的不是“实现一次上下文压缩”，而是建立一套可扩展、可组合、可调参的上下文治理框架。如果把流程写死在 `Engine` 里，短期能跑，后面很快会失控。

  可以从几个角度看。

  - **上下文治理不是单一动作，而是一组可能变化的策略。**
    `truncate`、`offload`、`summarize` 只是当前这章的三种策略。后面完全可能继续加 memory 写入策略、优先级保留策略、tool result 压缩策略、基于任务类型的差异化策略。如果这些都写死在 `Engine` 里，`Engine` 会变成一个不断膨胀的 if/else 中心。

  - **不同策略有不同触发条件。**
    不是每次都要截断，也不是每次都要摘要。`ShouldApply` 的价值就在于：每个策略自己决定“什么时候该出手”。这样 `Engine` 不需要理解每个策略的业务条件，只要负责统一调度。

  - **策略之间需要可组合，而不是二选一。**
    真实上下文治理通常不是“只选一种方法”，而是可能先 `offload`，再 `summarize`，最后还要 `truncate`。链式执行就是在表达：上下文治理是一个流水线，而不是一个单点函数。

  - **顺序本身就是策略的一部分。**
    先摘要再截断，和先截断再摘要，结果可能完全不同。一旦你把策略设计成链，就能把“执行顺序”也当成一种可调参数，而不是硬编码逻辑的一部分。

  - **更利于测试和替换。**
    现在每个 policy 都能单独测试，`Summarizer` 也能 fake 掉。如果所有逻辑都写在 `Engine` 里，测试会变成“大而全”的集成测试，很难定位边界行为。

  - **`Engine` 的职责会更清晰。**
    `Engine` 应该负责持有上下文状态、提供 turn 生命周期、统一执行 policy 链，而不应该负责知道每种上下文治理细节怎么实现。这就是典型的“调度器”和“策略实现”分离。

  所以更准确地说，`Policy` 设计成接口 + 链式执行，是为了把上下文工程从“写死的一套逻辑”提升成“可以持续演进的治理框架”。


### Q12. policy 链为什么有顺序，为什么不同阈值和参数会导致完全不同的运行行为，以及为什么这本质上是一个工程调参问题，不只是算法选择问题？

- **一句总结：**
  policy 链有顺序，是因为每个策略都会改写后续输入；阈值和参数会改变触发时机、处理范围和保留结构；因此上下文工程本质上是系统级调参问题，而不是单纯的算法二选一。

- **详细回答：**
  因为 `ch05` 里的上下文治理不是“选一个最好算法”就结束了，而是多种治理动作叠加后的系统行为。一旦是链式执行，顺序、阈值和参数都会直接改变最终上下文长什么样。

  可以分三层看。

  - **为什么 policy 链有顺序：**
    因为每个 policy 都会改写同一份上下文，前一个策略的输出就是后一个策略的输入。所以顺序不同，结果就不同。

    例如：先 `offload` 再 `summarize`，摘要器看到的是“预览 + 可恢复入口”，会更偏向保留外置结构；先 `summarize` 再 `offload`，很多长内容可能已经被摘要掉，后面根本没有东西可 offload；先 `truncate` 再 `summarize`，被截掉的历史连摘要机会都没有；先 `summarize` 再 `truncate`，则可能先保住主线，再删掉更早细节。所以顺序本身就是策略设计的一部分，不是实现细节。

  - **为什么不同阈值和参数会导致完全不同的运行行为：**
    因为它们决定了什么时候触发、一次处理多少、哪些消息受影响、保留区有多大。比如 `offload` 的 `UsageThreshold` 太低，系统会很早开始外置工具结果，上下文变轻，但模型会更频繁依赖 `load_storage`；`summarize` 的 `KeepRecentMessages` 太大，可摘要区就变小，摘要收益有限；`SummaryBatchSize` 太大，一次摘要信息更多，但摘要质量可能下降；`truncate` 的阈值太高，则会把上下文拖到很危险才动手，更容易“本地看着没超，模型侧先超窗”。所以参数不是微调，而是在决定系统偏“保守保真”还是偏“激进压缩”。

  - **为什么这本质上是工程调参问题，不只是算法选择：**
    因为真实系统里你关心的不只是“哪种方法理论更好”，而是整体运行效果：会不会太早压缩，影响回答质量；会不会太晚治理，导致超窗；模型会不会频繁去 `load_storage`；摘要会不会把关键细节抹掉；成本、延迟、稳定性怎么平衡。这些都不是单个算法能单独决定的，而是策略顺序、触发阈值、保留区大小、批量参数、模型上下文窗口和实际任务类型一起作用的结果。

  所以更准确地说，上下文工程不是“选 truncate / offload / summarize 中谁最强”，而是把多种策略按合适顺序和参数组装成一个在你任务上稳定工作的运行时系统。
### Q13. 消息什么时候保留、什么时候压缩、什么时候卸载、什么时候删除？

- **一句总结：**
  消息在“现在重要且值得占窗口”时保留，在“语义重要但原文不重要”时压缩，在“原文未来可能还要回看但现在不值得常驻”时卸载，在“价值已低且必须腾空间”时删除。

- **详细回答：**
  可以把这四个动作理解成对“历史信息价值”的四种处理决策。

  - **什么时候保留：**
    当一段消息仍然是当前任务推进所必需的，而且它的体积还在可接受范围内时，就应该原样保留。在 `ch05` 里，最典型的是最近几轮对话、最新的 tool 调用和结果，以及尚未进入 policy 可处理区的消息。本质上，保留意味着：这段信息现在既重要，又值得直接占用上下文窗口。

  - **什么时候压缩（summarize）：**
    当历史不能直接丢掉，但也没必要继续保留原文时，就适合压缩。典型场景是历史轮次很多、任务主线还需要记住、但原始细节已经没有逐字保留的必要。也就是说，压缩适合那种“语义还重要，但原始表达已经不重要”的信息。

  - **什么时候卸载（offload）：**
    当原始内容很长、很占窗口，而且未来可能还要回看全文时，就适合卸载。在这章当前实现里，主要是长 `tool` 输出。这类内容的特点是：当前不一定需要全文留在上下文里，但未来如果模型要精查细节，还可能需要原文。所以卸载适合那种“全文仍有价值，但不值得一直在线占窗口”的信息。

  - **什么时候删除（truncate）：**
    当一段历史已经既不值得保留原文，也不值得额外恢复，而且系统必须腾空间时，就只能删。这通常发生在上下文压力已经很高、更早历史相对当前任务价值更低、即使做进一步恢复也不划算的时候。删除适合那种“相对低价值，且系统已经需要硬腾窗口”的信息。

  如果把这四个动作压成一条决策链，可以理解为：先问这段信息现在还值不值得直接留在上下文里；值得，就保留。若不值得原样保留，再问语义还重不重要；重要，就压缩。若原文以后可能还要精确回看，再问要不要把全文外置；要，就卸载。若既不值得压缩保语义，也不值得额外存原文恢复，就删除。

  所以更本质地说，这四个动作不是四个平级 feature，而是四种不同的信息命运：保留是在线保留，压缩是保语义，卸载是保原文但离线化，删除是彻底放弃。

### Q14. 如果 `summarize` 把关键信息摘要错了，系统应该怎么兜底？

- **一句总结：**
  摘要出错的兜底思路是：别让摘要垄断事实来源，关键内容保原文可恢复，最近消息保留原文，摘要失败保守回退，必要时重读原文或校验摘要。

- **详细回答：**
  要把它当成“有损压缩可能出错”来设计，不能默认摘要一定可信。兜底不是一个点，而是一组机制。

  - **不要让摘要独占事实来源。**
    摘要适合保主线，不适合承诺保全部细节。系统里应该同时保留别的事实来源，比如最近几轮原始消息、被外置的原文、可重新读取的资源。这样摘要错了，系统还有别的证据链。

  - **关键内容优先 `offload`，不要只交给摘要。**
    对特别长、后面还可能精确依赖的内容，更稳的是先外置原文，再在上下文里留预览和恢复入口。这样摘要漏了细节，模型至少还能把原文拿回来。

  - **保留最近原始消息，不让它们过早进入摘要区。**
    最近消息通常最容易影响当前回答。把它们留在原文形态，能降低摘要误差直接伤到当前任务的概率。这也是 `KeepRecentMessages` 这类参数的真正价值。

  - **摘要失败时要保守回退。**
    如果摘要结果明显异常、为空、或者不满足最基本要求，系统应该宁可不替换原消息，也不要把一个不可信摘要写进正式上下文。原则是“宁可保守，不要错改”。

  - **摘要要能被重新生成或修正。**
    如果后面发现摘要不够，系统不应该只能接受错误结果。更稳的做法是允许基于原始历史重新摘要，或者对 running summary 增量修正。

  - **高风险场景加摘要质量校验。**
    更强的系统会在摘要后再做一层验证，比如检查关键实体、数字、约束、工具结果是否仍然存在，必要时让另一个模型做摘要审查。这会增加成本，但能换可靠性。

  - **冲突时优先相信更新、更具体的原始证据。**
    摘要本质上是压缩视图，不应压过更具体、更新的原始消息。一旦摘要和原始记录冲突，系统应该允许回到原文，而不是把摘要当绝对真相。

### Q15. token 是怎么计算的？

- **一句总结：**
  `ch05` 里 token 是通过 `cl100k_base` tokenizer 对每条消息的正文字符串做近似分词计数得到的，它用于上下文治理判断，不是精确计费值。

- **详细回答：**
  这章里 token 计算做得很简单，本质上是只对消息正文字符串做分词计数。

  看实现：`ch05/context/share.go`。

  - **编码器选择：**
    用的是 `tiktoken-go` 的 `cl100k_base` 编码器。这个编码器大体对应 OpenAI 这一代常见模型的 tokenizer 体系。

  - **计数入口：**
    入口函数是 `CountTokens(message shared.OpenAIMessage) int`。

  - **具体做法：**
    它先取出消息内容 `message.GetContent().AsAny()`，然后只处理一种情况：如果内容是 `*string`，就调用 `tokenEnc.Count(...)`，返回这个字符串被切成多少个 token。

  - **没算进去的东西：**
    当前实现没有精细计入 role 本身、tool call 结构化字段、function / tool schema、message 包装格式，以及 API 真正请求时的协议额外 token。所以它是一个近似估算，不是严格等于平台最终计费 token。

  - **这章为什么这样做也够用：**
    因为 `ch05` 的目标不是做计费精算，而是做上下文治理触发判断。对 policy 来说，更重要的是大致知道上下文是不是在快速膨胀、什么时候接近阈值。这种场景下，用正文近似计数就已经能工作。

  - **近似计数会不会正好踩线，但模型侧其实已经超长：**
    会，而且这是这类方案的真实风险。因为 `ch05` 当前算的是消息正文字符串的近似 token 数，但模型侧真正看的往往还包括 role 包装、tool call / tool result 结构、tools schema、system prompt 包装，以及 API 协议额外开销。所以完全可能出现本地估算看起来还没超，但真正发给模型后已经超窗的情况。这也是为什么工业系统不会把阈值顶到很满，而会提前留安全余量。`ch05` 当前的 `offload=0.40`、`summarize=0.60`、`truncate=0.85`，本质上就是在给这种不精确计数留 buffer。


### Q16. 为什么当前 policy 只在本地估算 token，而不结合服务端真实 usage 做反馈校准？

- **一句总结：**
  当前 policy 只用本地 token 估算，是因为这章先解决“上下文治理能不能工作”的问题；服务端真实 usage 校准更精细，但也更复杂、更依赖 provider，一般会放到下一阶段再接入。

- **详细回答：**
  因为 `ch05` 这一章的目标还是先把上下文治理框架跑通，而不是把“本地估算 + 服务端真实 usage + 动态校准”这整条闭环一次做完。

  更准确地说，这背后通常有四个原因。

  - **第一，当前实现优先解决“有没有治理框架”，不是“计量是否最精确”。**
    `Engine + Policy` 这套东西已经足够让系统开始统计上下文规模、触发压缩 / 卸载 / 截断、控制窗口增长。对教学章节来说，这一步优先级更高。如果一开始就把服务端 usage 校准、误差回填、动态预算全塞进来，会把主线复杂度拉高很多。

  - **第二，服务端 usage 不完全等于“当前本地上下文状态”。**
    服务端返回的 usage 是“这一次请求实际消耗了多少 token”，它受 system prompt、tool schema、协议包装、completion 输出，甚至某些厂商内部计量差异影响。但 `Policy` 要治理的是“现在这份上下文本身大概有多重”。这两者有关，但不是一一对应。要把它们用于校准，需要额外定义清楚校准哪一部分，以及怎么把单次 usage 映射回长期上下文估算。

  - **第三，流式、多厂商、tool 场景下的 usage 反馈并不总稳定。**
    有的服务端会返回 usage，有的不会；有的流式只有最后才给 usage；有的第三方兼容 OpenAI 协议但 usage 字段不完整。如果系统强依赖服务端 usage 才能做治理，鲁棒性会下降。本地估算虽然粗，但胜在统一、随时可用。

  - **第四，这章已经为后续校准预留了接口，但还没真正接上。**
    `CommitTurn(ctx, draft, Usage{PromptTokens: ...})` 已经说明作者意识到后面很可能要把服务端 usage 纳入上下文治理，只是当前还停在“先把接口留出来”的阶段。也就是说，这不是完全没考虑，而是章节实现还没走到那一步。

  所以为什么现在只做本地估算，而不做服务端 feedback 校准？一句话说就是：因为本章优先交付的是一个稳定、可运行、与 provider 弱耦合的上下文治理框架；服务端 usage 校准属于下一层精细化能力，接口已经预留，但闭环还没做。

### Q17. `offload + load_storage` 为什么还不算真正的长期记忆？

- **一句总结：**
  `offload + load_storage` 还不算真正的长期记忆，因为它只是把长内容从上下文里外置并提供按需回读能力，还没有做记忆选择、结构化组织、主动检索和长期生命周期管理。

- **详细回答：**
  因为 `offload + load_storage` 解决的是上下文外置和按需回读，而不是“记忆该如何被筛选、组织、检索和长期保留”。它更像一种“把当前上下文里太长的东西先搬出去”，而不是一个真正的 memory system。

  可以从几个角度区分。

  - **它没有做“记忆选择”，只是做“内容搬运”。**
    真正的长期记忆系统通常会先判断什么值得记、什么不值得记、记成什么结构。而 `offload` 当前并不判断“这段内容是否长期有价值”，它只是看到这是长 `tool` 消息、现在太占上下文，那就搬出去。这更像存储管理，不是记忆管理。

  - **它没有做“记忆组织”。**
    长期记忆通常会有某种组织形式，比如用户偏好、任务状态、项目事实、历史结论、可检索摘要。但 `offload` 存进去的只是原始长文本，外加一个 key。它没有把内容抽象成更高层的知识单元。

  - **它没有做“主动检索”。**
    真正的 memory 系统往往是当前任务来了，系统主动判断哪些记忆相关，并自动把相关记忆召回进上下文。而 `load_storage` 现在是模型先看到预览，自己决定要不要手动调用 tool 取全文。这是一种被动回读，不是主动 memory retrieval。

  - **它没有长期生命周期管理。**
    长期记忆系统通常还要关心记忆会不会过期、能不能更新、会不会冲突、要不要合并、怎样去重。`offload` 当前没有这些机制。它更像是一个简单的 key-value 外置存储。

  - **它保留的是原文，不是稳定知识。**
    长期记忆通常强调“把对后续长期有用的知识沉淀下来”。`offload` 保存的却常常是原始命令输出、文件全文、长工具响应。这些内容可能很长，也可能后面很少再有价值。它们更像原始档案，不像经过提炼的记忆。

  所以更准确地说，`offload + load_storage` 解决的是“上下文窗口装不下怎么办”，属于上下文工程 / 存储外置；而长期记忆解决的是“什么信息值得长期保留，并在未来任务中被有效召回”，属于记忆建模 / 检索 / 生命周期管理。

### Q18. 如果这章拿去做工业产品，最先要补的 3 个能力是什么？

- **一句总结：**
  如果把这章拿去做工业产品，最先要补的是：更可靠的 token / budget 校准、可恢复与可验证的摘要 / 外置机制，以及面向长期运行的记忆与观测体系。

- **详细回答：**
  如果把 `ch05` 直接拿去做工业产品，我会优先补这 3 个能力。

  - **第一，预算与计量闭环。**
    当前主要靠本地近似 token 估算做 policy 触发，这足够教学，但不够生产。工业系统首先要补的是：服务端真实 usage 回传、本地估算与真实 usage 的校准、安全余量控制，以及请求失败时的二次压缩兜底。否则一到多 provider、流式和复杂 tool schema 场景，就容易出现“本地看着没超，服务端先超窗”的问题。

  - **第二，可验证的上下文治理机制。**
    现在 `summarize`、`offload`、`truncate` 都能工作，但还缺少更强的可靠性保障。工业化时最先要补的是：摘要质量校验、关键事实保护、外置内容恢复链路校验、policy 执行结果审计，以及在治理失败时的保守回退策略。否则上下文治理一旦做错，就会变成“静默损坏历史”，排查成本很高。

  - **第三，真正的记忆与观测体系。**
    当前只有上下文治理，还没有完整的 memory 和 observability。工业产品至少要补：哪些信息值得长期记忆、记忆如何结构化组织、如何主动检索召回，以及每次 policy 是否触发、删了多少、压缩了什么、回答质量有没有受影响的观测指标。没有这一层，就很难把参数调优从“凭感觉”变成“可测量的工程系统”。

  更概括地说，教学版 `ch05` 已经回答了“上下文太长怎么办”，但工业版还必须进一步回答：怎么算得更准、压得更稳、出了问题怎么发现和恢复、长期信息怎么沉淀和利用。
